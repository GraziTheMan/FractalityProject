# Fractality Platform — Full Codebase Audit

**Date:** 2026-08-17
**Audited version:** v0.13.0 (commit `f83fec7`) → v0.13.1
**Scope:** the whole repository — 264 files, ~74k lines of JavaScript, 35 Python modules

---

## Executive summary

Before this audit, **the application could not be built, served, or loaded.**
Not "had bugs" — it could not start. Ten JavaScript files did not parse, five
Python modules did not compile, the package manifest contradicted every source
file in the repo, and the single line responsible for booting the 3D engine
called a method that did not exist.

After this audit the project builds, boots in a browser with zero console
errors, renders its 36-node test graph at interactive frame rates, and has a
test suite and a repeatable health check.

| | Before | After |
|---|---|---|
| JS files that parse | 95 / 105 | **all** |
| Python files that compile | 30 / 35 | **all except one archived file** |
| Unresolved relative imports | 40 | **0** outside `archive/` |
| Broken HTML asset references | 18 | **0** outside `archive/` |
| `npm run build` | did not exist | **succeeds** |
| Page loads without JS errors | no | **yes** |
| Automated tests | 3 empty placeholder files | **44 JS + 66 API + 16 live-DB integration** |

The single most useful finding is not any individual bug but the **cause**: the
overwhelming majority of defects trace to a handful of mechanical copy-paste
failure modes, each with a recognisable signature. Those signatures are now
encoded in `scripts/health-check.mjs`, so they cannot silently recur.

## Part 1 — Root causes

Rather than 60 unrelated bugs, this was five repeated mistakes.

### 1.1 Truncation at a copy limit (3 files, ~15 methods lost)

Three files were **exactly** 20,000 / 20,004 / 20,028 bytes and ended
mid-identifier:

```js
siblingEl.dataset.nodeId = node.s          // NodeInfoPanel.js, cut here
const audioAgent = this.agentNetwork.getNode('age   // FractalAIPrototype.js
import { Consciousn                        // ConsciousnessNode.js
```

A file ending mid-token at a round 20,000 bytes is not a coding error, it is a
chat window's copy ceiling. Two more files (`data-console.html` at 20,011 and
`DebugShell.html` at 20,039) share the signature and are still truncated in
`archive/`.

**What was lost.** `NodeInfoPanel.js` lost nine methods —
`_onTreeNodeClick`, `_navigateToNode`, `_expandNode`, `togglePin`,
`_setupEventListeners`, `_animateOpacity`, `_getScoreColor`,
`_getRelationshipLabel`, `_formatValue` — every one of them called from the
surviving code. `FractalAIPrototype.js` lost six.

**Fixed** by completing the cut method and reconstructing the missing ones
against their existing call sites. Navigation follows the `nodeSelected` window
event that `SearchInterface` already used, so the restored code matches the
project's own convention rather than inventing a new one.

### 1.2 Markdown rendering ate the source (5 Python files)

The clearest single diagnosis in the audit. Three `core/field_engines/` modules
contained **zero** occurrences of `__init__`, while their working sibling
`superionic_database_enhanced.py` contained four. The damage:

| Original | As committed |
|---|---|
| `def __init__(self):` | `def init(self):` |
| `if __name__ == "__main__":` | `if name == "main":` |
| `"""docstring"""` | bare text |
| `# comment` | bare text |
| two lines | one merged line |

Double underscores are Markdown's bold/italic markers. This code was pasted
from *rendered* Markdown, not from a code block — which also explains the
collapsed newlines (rendered paragraphs) and the stripped `"""` and `#`.

```python
# What was committed:
class OntologyGraph: def init(self): self.nodes = {} self.edges = defaultdict(list)

# What it had to be:
class OntologyGraph:
    def __init__(self):
        self.nodes = {}
        self.edges = defaultdict(list)
```

**Fixed** by reconstructing all five files. `field_glyph_generator.py` and
`superionic_database.py` were then run to confirm they produce correct output.

### 1.3 Multi-file AI responses pasted into one file (2 files)

When an assistant emits several files in one reply, the separators say where
each belongs. Those separators were pasted along with the code:

```js
// ===========================
// src/core/EventBus.js          ← this is a filename, not a comment
// Central event system
export class EventBus { ... }
```

`src/mobile/MobileApp.js` was **five** modules concatenated, and it imported
`EventBus`, `MobileConfig`, `HapticFeedback` and `AnimationEngine` from paths
that did not exist *while also defining all four in its own body* — plus, at
line 504, an import of itself. It failed to parse on
`Identifier 'EventBus' has already been declared`.

`src/ecs/ECS.js` had the same shape: it exported nothing at all, ran a demo
world at import time, and `main.js` imported `./ecs/components.js` and
`./ecs/systems/*.js` — the exact split the file's own comments described.

**Fixed** by splitting both at their separators, into the paths those
separators named.

### 1.4 Escaped template literals (4 files)

```js
this.root.innerHTML = \`
  <div class="menu-actions \${this.open ? 'open' : ''}">
```

`\`` and `\${` are what you get when a template literal is nested inside
another template literal and the outer layer is stripped. Four `ui/` modules
were unparseable because of it.

### 1.5 Divergent duplicates, where the *stale* copy was live

Four `main.js` files, two `index.html`, five `package.json`. The dangerous case
was not the duplication but which copy won:

- `public/components/radialMenu.js` (live) **lacked `setHandedness()`**.
  `mirrorToggle.js` calls it on every Mirror click, so the button threw a
  `TypeError`. The *archived* copy still had the method — the older file was the
  more complete one.
- `public/index.html` linked `./src/styles/main.css`, a path that only resolves
  from the repository root. It had been moved *into* `public/`, breaking all
  three stylesheet links.

## Part 2 — Findings that were not copy-paste damage

### 2.1 SECURITY: AI provider keys in browser code

**Severity: high.** `src/chat/FractalityChat.js` runs client-side and did this:

```js
this.apis = {
    claude: new Anthropic({ apiKey: config.claudeKey }),
    gpt: new OpenAI({ apiKey: config.openaiKey }),
    ...
```

fed from `src/config/chatConfig.js`:

```js
claudeKey: process.env.ANTHROPIC_API_KEY || 'your-claude-api-key',
```

Two independent problems:

1. **`process.env` does not exist in a browser bundle.** Reading it throws a
   `ReferenceError` at module load. So this code could never have run.
2. **Had it "worked", it would have been worse.** Any key reachable from client
   code is bundled into the JS served to every visitor, readable in devtools,
   and spendable against your quota.

**Action taken:** the key fields are now explicitly empty, with the reasoning
documented in place, and `chatConfig` reads an optional `VITE_AI_PROXY_URL`
instead. `FractalityChat` throws a clear error naming the missing credentials
rather than constructing SDK clients with `undefined`.

**Still outstanding:** the actual fix is a server-side proxy. `server.js` is the
natural home — it can hold real keys in its own environment. Until that exists
the chat module is intentionally not importable, and its three SDKs are
deliberately absent from `package.json`.

### 2.2 The packaging manifest contradicted the entire codebase

`package.json` declared `"type": "commonjs"` with dependencies of exactly
`express`, `socket.io` and `url`. Meanwhile:

- every file in `src/` is an ES module
- `src/` imports `three`, which was **not a dependency**
- `vite.config.js` existed, and `vite` was **not a dependency**
- `vite.config.js` pointed at `./index.html`, which **did not exist** (it was in `public/`)
- `server.js` served `__dirname` and fell back to a root `index.html`, so in
  production **every route 404'd**
- `server.js` had an explicit `/chat` route serving a `chat.html` that lives in the archive
- four *other* `package.json` files disagreed about name, version and module type

`render.yaml` compounded it: `buildCommand: npm install` with no build step, so
the deployed site would have served raw ES modules containing a bare `three`
import that no browser can resolve.

**Fixed.** One manifest, `type: module`, `three` + `vite` declared, real
scripts. `server.js` converted to ESM, serves `dist/` when built and warns when
not. `render.yaml` now builds. The four duplicate manifests are gone.

### 2.3 Modules imported but never written (3 files)

Not damage — code written against modules that were never created:

| Missing module | Imported by | Resolution |
|---|---|---|
| `src/intelligence/ResonanceEngine.js` | `MobileApp`, `ResonanceFeedController` | Implemented, local-only |
| `src/visualization/ParticleFieldRenderer.js` | `MobileApp` | Implemented, canvas-2D |
| `core/agent_systems/ExecutiveAgent.js` | `scripts/test_loop.js` | Implemented |
| `core/field_engines/phase_engine.py` | `consciousness_user.py` (×2 methods) | Implemented |

Each was written against the API its callers already assumed — method names,
arguments and return shapes were all recoverable from the call sites.

`phase_engine.py` is worth a note. `ConsciousnessUser` already declared
`LIQUID_THRESHOLD = 200.0  # Energy * frequency` and
`SUPERIONIC_THRESHOLD = 50000.0`. Taken literally, a brand-new user
(energy 100 × frequency 432 = 43,200) would classify as LIQUID immediately —
yet the enum documents `SOLID` as *"New users, fixed patterns"*. Driving phase
from the frequency **gain** over the 432 Hz baseline makes every threshold land
correctly: a new user has gain 0 → SOLID, and 100 × 500 Hz = 50,000 → SUPERIONIC.
The thresholds are read from the user class rather than duplicated.

### 2.4 A dead loader, and `THREE` undefined in four modules

`FractalityEngine`, `FractalityRenderer`, `AnimationSystem` and
`EnergyVisualizer` all began with:

```js
import { loadThreeJS, getEnvironmentInfo } from '../utils/ThreeJSLoader.js';
```

…and **never called either function**, then used a bare `THREE` that was
therefore always `undefined`. `ConsciousnessNode.js` used `THREE` 18 times with
no import at all.

The loader itself could not have helped: it is async and returns `{ THREE }`,
but every consumer used `THREE` synchronously in its constructor. It was also
the source of Vite's "dynamic import cannot be analyzed" warning.

**Fixed** with a static `import * as THREE from 'three'` in all five, which the
bundler resolves and tree-shakes. `ThreeJSLoader.js` is retained but is no
longer on the critical path.

### 2.5 The bug that kept the visualizer dark

`src/utils/appState.js` was nine lines:

```js
export const AppState = {
  currentView: 'bubble',
  setView(view) {
    const content = document.getElementById('content-view');
    content.innerHTML = `<div ...>Switched to: <strong>${view}</strong></div>`;
  }
};
```

But all three `main.js` variants contain:

```js
AppState.on('viewChanged', async (view) => {
  if (view === 'bubble' && !fractalityEngine) {
    fractalityEngine = new FractalityEngine('fractality-canvas');
    ...
```

`AppState` has no `on`. That line — the one responsible for constructing the
engine, loading data and starting the render loop — threw
`TypeError: AppState.on is not a function` and aborted the rest of module
initialisation. **The 3D visualizer had never run.**

A second bug hid behind it: `setView` overwrote `#content-view`'s `innerHTML`,
and `#fractality-canvas` is a child of `#content-view`. Any view switch would
have destroyed the canvas the renderer holds a reference to.

**Fixed.** `AppState` now has a real `on`/`off`/`emit` (async-aware, with
per-handler error isolation), placeholder text renders into its own element so
the canvas survives, and `main.js` sets an initial view so something is on
screen at load.

### 2.6 Neither stylesheet styled the actual page

`index.html` declares `#radial-menu`, `#state-indicator`, `#mirror-toggle`,
`#content-view`, `#biometric-panel`. But `main.css` styles `#canvas`,
`#ui-overlay`, `#controls` — an older DOM — and `mobile-menu.css` styles
`#menu-root`, `#menu-container` — `MenuController`'s DOM. Of the shell's
elements, only `#desktop-dock` had any rules.

The visible consequence: `#radial-menu` had no dimensions, so
`getBoundingClientRect()` returned ~0 and `RadialMenu.render()` stacked all
nine buttons on one point.

**Fixed** with `src/styles/shell.css`, matching the existing cyan-on-black
conventions. `RadialMenu` now also clamps its radii to its container and
re-lays-out on resize, so the fan is responsive instead of clipped.

### 2.7 Assorted correctness bugs

- `TriadicConsciousnessEngine` instantiated `SharedConsciousContext` **without
  importing it** — constructing the engine threw `ReferenceError`. Now tested.
- `main.js` called `testGenerator.generatePattern()`; the method is
  `generateTestPattern()`. Further, `'golden'` was not one of its cases despite
  `generateGoldenSpiral()` existing, so it would have silently fallen through
  to `default` and returned the trivial graph. Added `golden`/`spiral`/
  `balanced`/`organic` so the five patterns the README advertises are reachable.
- `def 8x8x8_cube_preparation` — a Python identifier cannot begin with a digit.
- `core/field_engines/superioronic_database.py` was misspelled ("superi-**ro**-onic").
  Two modules do `from superionic_database import SuperionicDatabase`, so they
  could never have imported it. Renaming fixed all three at once.
- `graph-chat-sync.js` imported `./init.js`; the file is at `src/main/init.js`,
  and it did not export `nodeGraph`.
- `FractalityRenderer` set `outputEncoding`/`sRGBEncoding`, removed in three r152+.
- `consciousness_backend/requirements.txt` was **empty** (2 bytes). Reconstructed
  from actual imports across the Python tree — 16 packages.
- `MainMenuRadial.js` used `assert { type: 'json' }`, a withdrawn proposal.
- The ECS ran a second uncapped `requestAnimationFrame` loop at a hardcoded
  1/60 delta. Now uses real elapsed time and pauses on tab hide.
- `MenuController.destroy()` calls `this.eventBus.off('node:focus')` with no
  handler argument, which is a silent no-op — listeners leak. **Not fixed**;
  flagged below.

### 2.8 Dead weight removed

- `transfer/` — a 25-byte `<!-- Placeholder HTML -->` and a 2-line manifest
- `json/` — two stale `package.json` copies parked in a folder named `json`
- `server/` — a stale manifest, an empty `start.md`, and a README byte-identical

## Part 5 — Follow-up: deployment preparation

A second pass, done while preparing the app to deploy at fractiverse.com as a
static site. It turned up four more defects, two of them security-relevant.

### 5.1 A second place shipping API keys to the browser

§2.1 covered `src/chat/`. `src/mobile/chat-ai-hub.js` was doing the same thing
independently and had been missed:

```js
export async function initAIBot(openaiKey) {
  const resp = await fetch('https://api.openai.com/v1/chat/completions', {
    headers: { 'Authorization': `Bearer ${openaiKey}` },
```

A raw OpenAI key, passed into client code, sent from the browser. Rewritten to
call a server-side proxy (`VITE_AI_PROXY_URL`) and to stay disabled until one is
configured. **Lesson for the audit itself:** finding one instance of a pattern is
a reason to grep for the pattern, not to close the finding.

### 5.2 Stored XSS in the feed renderer

`ResonanceFeedController._createPulseElement()` built markup with `innerHTML`
and interpolated `pulse.title`, `pulse.preview`, `author.name`, tags and
`media.url` **unescaped**. Harmless while the feed is seeded locally; the moment
strangers can post, a single title containing `<img src=x onerror=...>` executes
in every reader's browser.

Fixed by escaping every user-authored value and validating URLs through a new
`src/utils/sanitize.js` (`escapeHtml`, `safeUrl`, `safeCssValue`). `safeUrl`
rejects `javascript:`/`data:` schemes including control-character obfuscation
(`java\nscript:`), which a naive `startsWith` check misses. 12 tests cover the
payloads.

This is the highest-priority finding for the stated goal of a public social
feed. Note it is a *mitigation*, not a solution: the renderer still uses
`innerHTML`. Server-side validation is still required, and moving that renderer
to DOM construction would remove the class of bug entirely.

### 5.3 Named imports that resolved to `undefined`

Two files imported names their target never exported:

- `chat-ai-hub.js` imported `{ chatSocket }` from `chat-client.js`, which only
  exported `initChatUI`.
- `chat-ui.js` imported `{ initChatUI }` **from itself** — the same snippet had
  been pasted into both it and `mobile-ui.js`.

Both resolved to a real file, so the original health check passed them. It now
parses each module's exports and verifies named imports against them; verified
by deliberately breaking an import and confirming a non-zero exit.

### 5.4 Deploy-hostile hardcoded hosts

- `NodeBridge` hardcoded `http://localhost:8001` and probed it on every page
  load. On a deployed site that is unreachable, and on HTTPS it is blocked
  outright as mixed content — a guaranteed failed request for every visitor.
- `chat-client.js` hardcoded `https://thefractalityplatform.onrender.com`, a
  previous deployment, so any new deploy would have talked to the old one. It
  also opened the socket at *module import* time and loaded socket.io from a
  CDN.

Both now read from `src/config/deploy.js`, the single source for
environment-derived config. The CLI bridge defaults to localhost during `vite
dev` only; chat is disabled unless `VITE_SOCKET_URL` is set; socket.io-client
comes from npm via a dynamic import, so it is code-split out of the main bundle
(confirmed: 0 occurrences in `main-*.js`).

**Verified:** the production build now loads with **zero page errors and zero
failed network requests**, while `vite dev` still probes the CLI bridge, so the
local CLI workflow is intact.

### 5.5 The Cypher is now verified

The caveat that ran through Parts 3 and 4 — that `api/repository.py` had never
touched a real database — is closed. All 16 integration tests pass against a live
AuraDB Free instance in 32s.

Getting there took three fixes, two of them mine, and the run was worth it:

1. **A hardcoded database name.** `settings.neo4j_database` defaulted to `"neo4j"`
   and was passed explicitly to every session. Aura names the database after the
   **instance ID** (`1efeea86`), so every query failed with `DatabaseNotFound`.
   Now defaults to empty, meaning "let the server resolve its default".
2. **A `/health` endpoint that lied.** `verify_connectivity()` only proves the
   server answered; it does not check the database exists. The API booted cleanly
   and reported `{"database": "ok"}` for a service that could not serve one
   request. Health now runs a real query. Relatedly `apply_schema()` logged seven
   warnings and returned `0`, which reads as success to a caller not checking the
   count — it now raises when everything fails.
3. **Integration tests that could not pass.** The `driver` fixture was
   module-scoped while pytest-asyncio gives each test its own event loop, so the
   driver held sockets bound to a dead loop. Every test failed with "Future
   attached to a different loop" regardless of the database. Now function-scoped.

An assumption I asserted as fact and got wrong: current AuraDB issues the
**instance ID as the username**, not `neo4j`, and spells the variable
`NEO4J_USERNAME`. The diagnostic script actively warned users toward the wrong
value. Corrected, and `scripts/check_neo4j.py` now exists to give a one-line
diagnosis instead of a driver traceback.

One cosmetic wart: `deploy.js` reads env vars through a helper function, so Vite
cannot statically replace `import.meta.env.DEV`, and the string
`http://localhost:8001` remains in the bundle as dead weight (~25 bytes). The
runtime behaviour is correct; the literal is never used in production.

## Part 6 — Follow-up: mobile was unusable

Reported after the first deploy went live: *"on mobile it's too cluttered to be
able to do much of anything. I had to orient my phone in landscape to be able to
see the maps button."*

The landscape detail is the diagnosis. A phone in landscape is 844px wide, which
clears the 720px breakpoint — so the layout that worked was the **desktop** one,
and the mobile layout was the broken one.

### 6.1 The dock was hidden on exactly the devices that needed it

`index.html` marks the dock `class="desktop-dock desktop-only"`, and
`shell.css` had:

```css
@media (max-width: 720px) { .desktop-only { display: none !important; } }
```

So on a phone in portrait, **Maps, Search, Debug, Export and Import were all
absent from the page** — not small, not covered, gone. The comment justifying it
said the radial menu was the primary navigation on narrow screens, which was
true of the menu and false of everything the dock held.

A second defect in the same rule set would have collapsed the dock even if it
had been shown:

```css
max-width: min(760px, calc(100vw - 420px));   /* -30px on a 390px screen */
```

A negative `max-width` collapses the element to nothing.

The dock is now a bottom bar below 720px: fixed to the bottom edge, one
horizontally-scrollable row, `env(safe-area-inset-bottom)` padding for the home
indicator, and emoji-only labels — six labelled buttons need about three screen
widths, six glyphs need 280px.

`--dock-height` in `shell.css` is now the single number every bottom-anchored
element measures from (0 on desktop, where the dock sits at the top). Previously
`NodeInfoPanel`, `NodeDebugPanel`, the mirror toggle and the home button each
hardcoded `bottom: 20px`, i.e. underneath wherever the dock ended up.

### 6.2 The breakpoint needed a height test, not just a width one

Fixing width alone left landscape phones on the desktop layout, where the dock
wrapped to two rows and the 364px-tall performance overlay filled a 390px-tall
screen. The compact layout now triggers on `(max-width: 720px), (max-height:
500px)`, and `PerformanceDashboard._isNarrowScreen()` applies the same test so
CSS and JS cannot disagree.

### 6.3 The radial menu's own layout was wrong, not just cramped

`RadialMenu.render()` spaced its nine items by equal **angle** across a
180-degree arc. Near the poles of an ellipse `sin()` flattens out, so the
outermost pair ended up ~13px apart vertically while the chips are ~35px tall.
The visible result on a phone: `🧠 Mindmap` rendered underneath `👥 Social`.

Shrinking the fan to fit the screen made it worse, because the gap is
`(height - 48) / 8`.

It now distributes items by equal **vertical** spacing, tracing the same ellipse
parameterised by y instead of by angle. The gap is `2 * radiusY / (count - 1)`
everywhere, so whether the labels fit is a property of the box rather than of
which end of the fan you look at. `radiusX` is also clamped against the
*measured* width of the widest label instead of a guessed 56px margin.

This is a fix to the existing component, not the replacement in item 3 below —
that is still outstanding and still the agreed direction.

### 6.4 The node info panel could never appear on a phone

`FractalityEngine` showed it from `_handleMouseMove` only. There is no
`mousemove` on a touch screen, so tapping a node focused it and showed nothing.

Three things had to change together:

- `_handleClick` now shows the panel too (`touchstart` already routes there).
- `show(node, { immediate: true })` skips the hover delay. Without that the
  tap-synthesised `mousemove` — which fires *before* `click` — lands on empty
  space, calls `hide()`, and cancels the pending show.
- The panel is **sticky** once opened by a deliberate tap, since there is no
  pointer-out event to close it, and it gained a **✕ button**. It had only a pin
  button, so on touch it would have appeared once and then covered the bottom of
  the screen permanently.

The close glyph is `U+00D7`, not the heavier `U+2715`: the latter is missing from
some Android and Linux font stacks and renders as an empty box, which for a close
button means the panel looks impossible to dismiss. That was caught in a
screenshot, not in the DOM.

### 6.5 Clicking a node silently stopped working — the real "pyramid" bug

Found while testing the above, and the most consequential item here.

`THREE.InstancedMesh.raycast()` rejects a ray outright if it misses
`this.boundingSphere`, and computes that sphere exactly once — on the first
raycast — then caches it forever. The instances in this app move every frame
(layout, animation, focus changes), and `_setGeometry()` swaps
`instancedMesh.geometry` on every quality change without invalidating anything.

So after the layout drifted, or after adaptive quality switched to low-poly,
**clicking or tapping a bubble did nothing at all**: no selection, no panel, no
error in the console. The renderer now nulls `boundingSphere` and `boundingBox`
after each matrix update and on every geometry swap, which makes `raycast()`
recompute on demand — one pass over the visible instances, and only on a real
pointer event.

This is very likely part of what was reported a year ago as *"the bubbles turn
into pyramids when I click anything and don't turn back."* The pyramids
themselves were §2.5's geometry-swap bug; the unresponsiveness afterwards was
this.

### 6.6 Smaller things in the same pass

- **The Search dock button called `show()`, never `hide()`.** Pressing it twice
  reopened an already-open panel. Escape and ✕ covered it on desktop; on a phone
  the panel then sat over the canvas absorbing taps meant for the map.
  `SearchInterface.toggle()` added.
- **`FractalityEngine.togglePerformanceMonitor()` had no caller anywhere.** The
  overlay was on by default with no way to dismiss it. It now defaults off on
  compact screens and has a `📈` dock button.
- **The CLI bridge controls were dead weight in production.** `hasCliBridge()`
  existed and was never called, so a deployed phone showed an Auto-Sync button
  that could only fail, a permanently-red "CLI Disconnected" light, and a
  5-second polling timer with nothing to poll. All three are now conditional.
  Export/Import stay — they are file download/upload and work anywhere.
- **`fractalityEngine.navigateToNode()` does not exist.** The method is
  `setFocus()`. Both call sites in `main.js` threw a `TypeError`, which means
  clicking a search result and pressing "Navigate Here" had never worked.
- **`.perf-dashboard.hidden` only set `opacity: 0`**, leaving an invisible
  overlay eating touches. It happened to work because `shell.css` forces
  `display: none` on `.hidden` globally — a panel should not depend on another
  stylesheet for that.
- **Notification toasts** were anchored right with no left bound, so a long
  message ran off the side of a phone.
- **`MapsPanel._describe()`** rendered a failed cross-origin fetch as the raw
  browser string `Failed to fetch`. On Render's free tier that is almost always
  a cold start, so it now says so and points at the refresh button. Matched by
  error *shape*, since the message differs per browser (Chrome "Failed to fetch",
  Safari "Load failed", Firefox "NetworkError when attempting to...").

### 6.7 Why none of this was caught earlier

Every item above is invisible to `npm run health`, which parses files. Each one
needed a browser at a phone viewport, and two of them needed a *screenshot*
specifically — the overlapping menu labels and the blank close button were both
perfectly well-formed DOM.

`npm run browser-check` (`scripts/browser-check.mjs`) now covers this. It drives
the built site in Chromium at 390x844, 844x390 and 1440x900 and asserts:

| Check | Catches |
|---|---|
| `elementFromPoint` on every control | elements present but covered, zero-size, or off screen |
| pairwise rect intersection of menu items | overlapping labels |
| `documentElement.scrollWidth > innerWidth` | horizontal overflow |
| second press on each dock button | panels that open but cannot be closed |
| real `touchscreen.tap` on a raycast-located node | touch paths that only work with a mouse |
| controls after `scrollIntoView` | actions stranded below a scroll fold |
| `setQuality()` across the hysteresis band | geometry that changes one way only |
| raycast after a geometry swap | stale `InstancedMesh` bounds |
| `pageerror` | uncaught exceptions on load or interaction |

Verified to gate: reinstating the `display: none !important` rule makes it
report six unreachable dock buttons and exit 1.

Playwright is deliberately **not** in `package.json` — it pulls a browser
download that every deploy would pay for. The script skips with instructions
when it is absent, and `npm run health` records that choice as a note rather
than a warning.

## Part 7 — Follow-up: a save that worked looked like a save that failed

Reported from a phone, with a screenshot: signed in, `💾 Save current` worked,
and the panel then read **"Could not reach the server"** with an empty list and
no visible way to share anything.

### 7.1 Reading the screenshot

`saveCurrent()` ends with `await this.refresh()`. So the sequence was: the write
succeeded, and the list request **immediately after it** failed at the transport
layer. That rules out the explanation the message was offering — a server that
had just accepted a POST is not cold-starting.

Three separate defects combined to produce that screen.

### 7.2 A committed save was reported as a failure

`refresh()` writes its own error into the status line, so its failure erased the
`Saved "…"` message that had just been written. The user is told their save
failed when the data is safely in Neo4j — the worst possible direction for this
error to lean, because the natural response is to try again and create
duplicates.

Writes now report through `_refreshAfterWrite()`, which keeps both facts:

> Saved "My Mind Map" — your map is saved. Press 🔗 Share for its link. The list
> could not be reloaded: …

`refresh()` returns `{ ok, message }` rather than only painting a status, so a
caller can tell what happened instead of inferring it from CSS classes.

### 7.3 Share existed only inside a list row

The only Share button was rendered per-map in `_renderList()`. When the list
request fails there are no rows, so there is no Share button — the control was
missing in precisely the situation where the user most needs it, which is why
the answer to "how do I share it" was "you cannot".

The map is known at that point: `saveCurrent()` sets `this.currentMap`. Sharing
never needed the list. There is now a `🔗 Share` button in the panel's action
row that acts on the current map, disabled only when there is genuinely nothing
loaded. All assignments to `currentMap` go through `_setCurrentMap()` so the
button cannot drift out of sync with what it would act on.

### 7.4 One transport hiccup was a hard failure

A single failed `fetch` ended the operation. A Render instance that is cold,
restarting, or was just killed refuses connections for a few seconds — worth
waiting out rather than reporting as a dead server.

`_request()` now retries transport failures with backoff (1.5s, 3s). The
important restriction:

**Only reads are retried.** `fetch` rejecting does not mean the server did not
process the request — the response may simply have been lost. Retrying a
`createMap` would create two maps. Writes get `retries = 0` and fail loudly.
There is a test for this, and it is mutation-checked: making writes retryable
makes it fail.

### 7.5 The error message asserted a cause it could not know

The previous wording blamed idle wake-up. The browser deliberately withholds the
reason for a failed cross-origin fetch, and cold start, a restart, a dropped
connection and **a CORS rejection** are indistinguishable from JavaScript.

So the panel now finds out instead of guessing. On a transport failure it probes
`/health`, which needs no auth and touches no data:

| `/health` | Conclusion shown |
|---|---|
| no answer | the service is down or restarting — check the logs |
| answers, `database`/`auth` not ok | up but not ready, naming which |
| answers, everything ok | this request specifically was blocked; the usual cause is CORS, and `CORS_ORIGIN` must list this exact origin |

That last row is the useful one, and it is the most likely explanation for the
reported screenshot: `/maps` is a *credentialed* cross-origin request, so it
fails wholesale if the API's `CORS_ORIGIN` does not match the site's origin
exactly — scheme, host and `www.` included.

One bug of mine surfaced while testing this: `_diagnose()` was not awaited, so it
resolved *after* `_refreshAfterWrite()` had written its status and silently
overwrote it — the "your map is saved" reassurance was replaced by the CORS
diagnosis. It now returns text for the caller to place, so the two cannot race.

### 7.6 The diagnosis itself was wrong

The first version of §7.5 shipped with a flaw that showed up immediately: on the
next report the panel said *"The API is not reachable at all — /health does not
answer either"*, while the owner noted they had only listed the `www` origin in
`CORS_ORIGIN`. Those two statements are inconsistent, and the panel was the one
that was wrong.

`checkHealth()` goes through `_request()`, which attaches an `Authorization`
header whenever someone is signed in. That makes it a **credentialed
cross-origin request**, so a CORS misconfiguration blocks `/health` exactly as it
blocks `/maps`. Using it to decide whether the server is alive is circular: it
cannot report on a failure mode that also suppresses it.

Worse, no ordinary `fetch` can settle this. Even without the auth header the
response still needs `Access-Control-Allow-Origin` before JavaScript may read
it, so "server gone" and "server fine, CORS blocking" are the same `TypeError`.

`MindMapClient.probeReachable()` resolves it with `mode: 'no-cors'`. That still
sends the request; it only makes the response opaque, so status and body cannot
be read. Which is enough — the promise **resolves** when a server answered and
**rejects** when no connection could be made:

| readable `/health` | `no-cors` probe | Conclusion |
|---|---|---|
| answers | — | up; report any `database`/`auth` problems it names |
| fails | resolves | **up, and CORS is blocking** |
| fails | rejects | genuinely down, restarting, or wrong URL |

It deliberately sends no headers: any non-safelisted header would take the
request back out of no-cors mode and reintroduce the failure it exists to see
past. There is a test asserting that.

When it is CORS, the message now names the origin to allow by reading
`window.location.origin` from the page — which removes the guesswork that caused
this in the first place, since `https://www.fractiverse.com` and
`https://fractiverse.com` are different origins and only one of them was listed.

Mutation-checked: replacing the probe with `const reachable = false` makes the
browser check report the exact wrong message that was on the owner's screen.

### 7.7 Coverage

`tests/mindMapClient.test.js` (9 tests) covers the transport layer: per-browser
error shapes, retry counts, that HTTP errors are never retried, that writes are
never retried, and that `checkHealth()` distinguishes unreachable from
up-but-broken.

`npm run browser-check` gained two sections. The first stubs the API into exactly
the reported state — POST succeeds, GET fails at the transport layer, `/health`
answers — and asserts the save is not reported as an error, that both facts
survive in the status, that Share works without the list, that the read was
retried twice, and that **the write was sent exactly once**. The second drives
the two indistinguishable failures (CORS blocking versus nothing listening) and
asserts each produces its own diagnosis and not the other's, and that the CORS
message names the page's actual origin.

## Part 8 — CORS confirmed, and a toast styled from two places

### 8.1 The save/share loop is verified end to end

`CORS_ORIGIN` was listing only `https://www.fractiverse.com`. Adding both
origins fixed it:

```
CORS_ORIGIN = https://fractiverse.com,https://www.fractiverse.com
```

With that in place the owner confirmed the whole loop on a phone: save, list,
open, share, **and the share link opening for an anonymous visitor in an
incognito window.** That single path exercises Clerk auth, the Cypher in
`api/repository.py`, share-token authorization and the graph adapter together,
which is the check `docs/DEPLOYMENT.md` asks for. So the diagnostic added in
§7.6 was right, and the cause was the one it named.

### 8.2 The toast was 814px tall and 185px off the left edge

Reported as "the side bar is cut off on the left side". It was not a sidebar —
it was the notification toast, and its geometry measured:

```
x: -175   y: 10   w: 370   h: 814     (viewport 390x844)
```

**Two stylesheets styled `.notification`.** `src/styles/main.css` had a rule for
it — part of the older DOM that stylesheet targets, per the note in
`index.html` — and `showNotification()` in `src/main.js` injected another.

Neither wins as a whole. CSS resolves each *property* independently, so the
injected rule (appended to `<head>` after the link tags) won `top`, `right`,
`left` and `border`, while main.css supplied two declarations nothing overrode:

| From main.css | Effect once combined |
|---|---|
| `bottom: 20px` | with `top: 10px` also set, the box stretches to 814px tall |
| `transform: translateX(-50%)` | shifts it left by half its width: 10 − 185 = **−175px** |

The DOM was perfectly well formed. Only the computed geometry was wrong, which
is why the earlier passes never saw it.

The fix is a **unique class name** — `.fractality-toast` — rather than another
layer of overrides, so no stylesheet written for a different DOM can reach the
element at all. Its own `@keyframes` are prefixed too: keyframe names are global,
and main.css defined its own `slideUp`. The rule now also states every edge
explicitly (`bottom: auto; left: auto; transform: none`) so a future collision
cannot supply one, and the stale `.notification` rules plus the orphaned
`slideUp`/`slideDown` keyframes were deleted from main.css rather than corrected
— a second definition is the bug, and keeping a fixed one invites it back.

Worth noting how this one was introduced: by me, in Part 6.6, adding a mobile
media query to a rule set that was already in a fight it did not know about.

### 8.3 Two new guards, because this is a whole class of bug

**Static.** `npm run health` now compares layout declarations across every
stylesheet *and* every CSS template literal injected from JS, and warns when the
same base selector has the same layout property set from more than one place —
the situation where the outcome depends on load order. Only positioning and
layout properties are compared: sharing a colour is usually deliberate, sharing
an edge or a transform is how elements end up off screen.

It immediately found five more latent collisions (`.hidden`, `.info-row`,
`.result-item`, `.result-header`, `.header-controls` — main.css against
component-injected styles). None currently misrenders, and they are left as
visible warnings rather than churned.

**Runtime.** `npm run browser-check` now raises a toast and asserts it sits
inside the viewport and is not stretched past 40% of the screen height, since
"both opposing edges set" is exactly what that measures.

Both were mutation-checked, and they fail in a usefully different way:

- Re-adding a competing `.fractality-toast` rule to main.css → **the static check
  warns** (`contesting: position, bottom, left, transform`) while the browser
  check stays green, because the explicit edge resets make the collision
  harmless. Correct on both counts: latent risk, no live defect.
- Removing the edge resets *and* re-adding the rule → **the browser check fails
  with `x: -175 … h: 814`**, the owner's exact numbers.

That division is the point. The static check finds the fragile arrangement; the
browser check finds the actual misrender.

### 8.4 One more thing this run caught

The first attempt at the new toast CSS did not build. A comment inside the
injected template read `` Leaving `bottom` unset `` — and a backtick inside a
template literal ends the template literal. Vite failed with
`Expected ';', '}' or <eof>`.

That is Part 1.4's failure mode exactly, reintroduced by hand rather than by
paste, which is a fair reminder that the check exists because the mistake is easy
rather than because chat windows are uniquely bad at it.

The brain-emoji button reported *"Debug panel not available (CACE engine not

It now roots the tree at the highest visible *ancestor* (guarded against cyclic

## Part 10 — Node Manager and Cone view, and a correction

Part 9 asserted that "Bubble and Cone were never separate surfaces — they are
layout algorithms". That was wrong about Cone, and it also treated the Node
Manager as covered by the node inspector, which it is not. Both are distinct
features with distinct purposes, described by the owner as:

> The Node Manager is like a file system organizer for the nodes... It's the UI
> for editing the actual relationships of the nodes, allowing you to see more
> than what the display otherwise would, because the idea is for child nodes to
> be hidden inside of parent nodes until that parent is selected and visited.

> Cone view... the top node is a single point at the highest tier (Tier 0), and
> the further down the tiers you go, the more nodes exist in each tier, hence a
> widening of the cone. The idea was that it would be a 2d side view of a cone
> that can be swiped left or right to "spin" the cone, and swiped up or down to
> view higher or lower tiers.

### 10.1 Why the Node Manager is not optional

The 3D view shows very little on purpose: children live inside their parent and
only appear once that parent is visited, so even within one tier you see only the
children of the node you selected. That is the point of the visualisation, and it
makes reorganising impossible — **you cannot move a node to somewhere you cannot
see.**

So the two surfaces divide cleanly: the 3D view reads, the Node Manager edits.

### 10.2 The graph had no edit operations at all

`NodeGraph` had `addNode`, `getNode`, `getChildren`, `getSiblings`,
`getNodesAtDepth` — and nothing else. No remove, no reparent, no reorder. It also
had **two competing sources of truth for children**: `parent.childIds` (an array)
and `childIndex` (a `Set`, derived from each child's `parentId`), which `addNode`
populated while never touching `childIds`.

`childIds` is now the ordered authority and `getChildren` reads it, because a Set
cannot express order and an outline whose "move up" does nothing is not an
outline. `childIndex` and `depthIndex` are derived and maintained by every
mutation.

The new operations: `createNode`, `removeNode`, `setParent`,
`moveWithinSiblings`, `promote`, `demote`, `renameNode`, `getDescendantIds`,
`getRootNodes`, `rebuildIndices`.

Decisions worth recording:

- **`depth` IS the tier**, so reparenting renumbers the whole moved subtree, not
  just the node that moved. Done iteratively — a deep chain is entirely possible
  in a user-built map and this must not depend on stack depth.
- **Cycles are refused.** `setParent` rejects a move into the node's own
  descendant, which would detach that subtree from the graph and hang every
  traversal. `getDescendantIds` is itself cycle-safe, since imported data can
  already describe a loop.
- **Deleting a node with children is two different intentions.** `cascade`
  removes the subtree; `promote` keeps the children and splices them into the
  hole, preserving their order relative to their former uncles. The UI asks
  rather than guessing, because guessing wrong loses work either way.
- **`demote` only uses the preceding sibling.** Falling back to the following one
  would silently reorder the outline as a side effect of an indent.

`tests/graphEditing.test.js` covers this — 24 tests, most of which re-assert the
same two invariants after every operation, because neither is visible from the
UI: every node's depth equals its parent's + 1, and `childIds`, `parentId`,
`childIndex` and `depthIndex` all agree. A bug here does not throw; it produces a
corrupted map that then gets saved to Neo4j.

### 10.3 The Node Manager

`src/ui/NodeManagerPanel.js`. A full outline of the graph — every node, not just
the visible ones — with tier numbers, child counts, expand/collapse, and eight
actions: add child, add sibling, rename, move out a tier, move in a tier, reorder
up, reorder down, delete.

Selecting a row also focuses that node in the 3D view, so the two surfaces stay
pointed at the same thing; the row the 3D view is looking at is marked separately
from the row you have selected.

Actions that cannot apply say why — "Already at tier 0", "Nothing above it to
move into" — following the same rule as the dock. Every edit calls
`engine.notifyGraphChanged()`, which is new and necessary: `loadData()` was the
only thing that re-analysed the graph, and it also resets focus, so using it
after an edit would throw the user back to the root each time they added a node.
Three caches would otherwise serve stale answers — the family view's 1-second
selection cache, the CACE analysis, and the layout.

### 10.4 The Cone view

`src/ui/ConeView.js`. A 2D side elevation on a canvas, driven by two gestures:
drag sideways to spin, drag up and down to travel the tiers. Pointer events, so
one code path covers touch, mouse and pen.

Nodes are laid out as a **cone tree**: each subtree owns a wedge of the circle,
divided among its children in proportion to how many leaves each contains.
Weighting by leaf count rather than splitting evenly stops a branch with one
child claiming as much of the circle as a branch with thirty, which is what makes
the widening legible rather than decorative.

The projection is a genuine side view — horizontal position is `sin` of the
angle, and `cos` only decides how near the viewer a node is, feeding size,
opacity and paint order. Tier rings are drawn as the ellipse a circle makes seen
nearly edge-on.

Only the front third of the current tier is labelled; wider than that and the
labels overlap, which is worse than not labelling them. The 3D engine is paused
while the cone covers the screen — otherwise it renders frames nobody can see,
which on a phone is battery spent on nothing.

### 10.5 The default map's tiers were wrong, and had always been

Found by the new browser check, not by looking: **15 of the 36 nodes in the
default generated map had a depth equal to their parent's.**

`TestDataGenerator.generateGoldenSpiral()` reassigned its `parent` variable to
the first child *inside* the loop that was still creating that level's children.
So the second and later children of a level were attached to their own sibling
while still being given the level's depth:

```js
for (let i = 0; i < childCount; i++) {
    const child = new NodeData(id, level + 1, {...});
    child.parentId = parent.id;      // `parent` already moved on
    if (i === 0) parent = child;     // ...here, mid-loop
}
```

Since depth is the tier, that made the tier numbers, the cone view's rings and
the family layout wrong together. Nothing noticed because nothing checked — the
3D view draws whatever positions it is given.

Fixed two ways, deliberately: the generator now pins the level's parent before
the inner loop and derives depth from `levelParent.depth + 1` so the two cannot
disagree again; and `loadData()` calls `rebuildIndices()` on every graph it
receives, whatever produced it. Graphs arrive from three places — the generator,
an imported file, the API — and any of them can carry a depth that disagrees with
its parent links. Normalising once at the boundary means every consumer
downstream can take `depth` literally.

### 10.6 A test that passed while asserting nothing

The first version of the generator regression test called
`generator.generate('spiral', …)`. There is no `generate()` method — the real
ones are `generateGoldenSpiral()`, `generateBalancedTree()`, `generateOrganic()`
and `generateTestPattern()`. It was wrapped in `try { … } catch { continue }`, so
all three patterns threw, all three were skipped, and the test reported success.

Caught only by mutation-testing it: reverting the generator fix left the suite
green. Rewritten to name each method explicitly with no swallowing catch, it now
fails with `goldenSpiral produced 15 node(s) whose depth disagrees with its
parent` — the original defect, exactly.

The lesson is narrower than "write better tests": a `catch` that continues turns
a test into a no-op, and a green suite is not evidence unless something has been
seen to make it red.

### 10.7 Coverage

`npm run browser-check` gained two sections, now 82 checks total.

**Node Manager** — that the outline lists *all* nodes rather than only the ones
the 3D view shows, that each of the seven edit actions has the right effect on
the node count, and, after every single edit, that the graph is still
structurally consistent. That last assertion is what found §10.5.

**Cone view** — that it opens unclipped, that every node is hit-testable, that a
sideways drag spins without changing tier, that a vertical drag changes tier and
settles on a whole number, that tier travel clamps at both ends, that the readout
matches the tier, that tapping a node selects it, and that the 3D engine is
paused while covered and resumed on close.

## Part 11 — The feed

Outstanding item 2 — *"`ResonanceEngine` has no network behind it... the social
half of 'social mind mapping' does not exist yet"* — is now built. Text and links
only; images are still blocked on object storage.

### 11.1 What the design brief actually asked for

> I also like the idea of having a "newsfeed" where people can scroll through
> things that their friends or maybe other random people post as text content,
> links, photos and whatnot. I don't want it to be the main thing, but rather a
> feature to help replace the scrolling of modern corporate social media.

"Replace the scrolling" is a design constraint, not a throwaway. Two things follow
from it directly, and both are choices rather than gaps:

- **No infinite scroll.** A "Load more" button, so continuing is a decision.
- **No ranking.** Strictly reverse-chronological, so the order is explicable.

A feed you can reach the end of is the point.

### 11.2 A separate component, not a retrofit

`ResonanceFeedController` already existed, and reusing it was the obvious move
until the cost showed up: it is styled entirely by `mobile-menu.css`, which
`index.html` does not load, and which targets MenuController's DOM (`#menu-root`,
`#menu-container`). Loading it would collide with the shell.

So `src/ui/FeedPanel.js` is new, with self-contained styles, and
`ResonanceFeedController` stays with the mobile app it was written for.

Its classes are prefixed `pulsefeed-`, not `feed-`, and that was not a guess:
`npm run health` flagged `.feed-title` as styled from two places the moment the
first version was written. The check added in Part 8 earned its keep on the very
next component.

### 11.3 Backend

```
(:User)-[:POSTED]->(:Pulse)
(:User)-[:RESONATED_WITH]->(:Pulse)
(:User)-[:REPORTED {reason, at}]->(:Pulse)
(:User)-[:BLOCKED]->(:User)
```

`resonators` is a count of relationships and `resonance` is derived from it. A
stored counter could drift from the relationships it summarises, and a like count
that disagrees with who liked it is worse than a slower query.

`MERGE` for resonance, reports and blocks, so all three are idempotent — a double
tap cannot make two relationships, and one person cannot inflate a report count by
pressing repeatedly.

The block filter lives **inside** the feed query. Filtering in Python afterwards
would make `limit` mean "up to N, minus however many were blocked", so blocking a
prolific poster would quietly produce short pages.

### 11.4 Moderation was built with it, not after it

`api/README.md` has said since Part 5 that a public feed needs report/block flows,
admin delete and rate limiting *before* it accepts content from strangers — and
that this carries legal obligations, not just product ones. Shipping the feed
without them would have made that note a lie.

| Control | How |
|---|---|
| Delete your own post | ownership is in the Cypher `MATCH`, so there is no check-then-act window and no way to reach another author's pulse |
| Report | fixed reason list, one report per reporter |
| Block | hides an author from *your* feed only; self-blocking refused, since it would silently empty your own |
| Rate limit | 20 posts/hour, counted from stored pulses |

The rate limit deliberately does not use an in-process counter: Render runs more
than one instance, so a per-process counter would hand each of them a separate
allowance.

Report reasons are a fixed list rather than free text. The reason is a routing
signal for a human, and an open text field on a report endpoint is itself an abuse
channel.

Two things are still missing and are recorded as such: an **admin review queue**
(there is no admin role in this project yet — reports go to the service log at
warning level) and **image scanning**, which cannot exist before image uploads do.

### 11.5 Hostile content is in the fixture, not a separate test

The feed renders text written by strangers, which makes it the one component where
a convenient template literal is a stored-XSS vector. So the browser check's feed
fixture includes a post whose title is `<img src=x onerror=...>`, whose body is a
`<script>`, whose author name is `<b>Evil</b>`, and whose link is a `javascript:`
URL.

That fixture found a real bug immediately. `safeUrl()` returns **`null`** for a URL
it will not vouch for; the first version of the panel compared against `'#'`:

```js
const href = safeUrl(pulse.media.url);
if (href !== '#') { link.href = href; }     // null !== '#', so this ran
```

`link.href = null` renders as the literal string `"null"`, which is inert — so the
`javascript:` URL did not execute, by luck rather than by design. A different
sentinel, or a browser that resolved `null` differently, and it would have been a
working injection.

A second, subtler point came out of the fix: the link's `href` is assigned the
**original** URL, not `safeUrl`'s return value. `safeUrl` HTML-escapes what it
vouches for, which is correct for `innerHTML` and wrong for a property — a query
string containing `&` would become `&amp;`, i.e. a different URL. The scheme has
already been checked by then, so the raw value is the safe one to assign. There is
a check asserting `?a=1&b=2` survives intact.

Mutation-checked: changing one `textContent` to `innerHTML` makes the hostile post
execute (`window.__pwned = 1`) and the check reports it.

### 11.6 What is NOT verified

**The feed's Cypher has never run against a database.** The 17 integration tests
were written alongside the queries, and they are the only thing that would catch a
mistyped relationship name or a `WHERE` clause that silently matches nothing — but
this environment has no Neo4j, no Docker daemon, and no route to download one
(`dist.neo4j.org` is blocked by the proxy, as is `fractiverse.com`).

The 35 router tests do run, and cover authorization, rate limiting and validation
with the repository stubbed. That is a different guarantee, and it is not a
substitute.

So: **run `pytest api/tests/test_integration_neo4j.py -v` before trusting the feed
with anything.** This is exactly the position the mind-map Cypher was in at the
end of Part 5, and it stayed there until it was run against live AuraDB — at which
point it passed, but only because a fixture-scope bug had already been fixed by
reading it very carefully.

### 11.7 Two bugs of my own, found by running things

- **A whitespace-only title was accepted.** `Field(min_length=1)` runs *before* a
  plain `field_validator`, so `"   "` satisfied the constraint as three characters
  and was then stripped to empty. Fixed with `mode="before"`, so trimming happens
  first and the constraint sees what will actually be stored.
- **The `safeUrl` sentinel**, above.

Both were found by executing the code rather than reading it — the first by a test
asserting an empty title is refused, the second by putting a `javascript:` URL in
a fixture.

## Part 12 — Turtle export, and the export that had never worked

Asked as a design question — *"instead of mind maps saving and exporting/importing
as json files, would it make sense to have it be .ttl files instead? we're kind of
creating ontological maps here"* — and it is a good instinct. These maps are
concept hierarchies with labels, types and tags, which is what RDF is for.

### 12.1 Interchange format, not internal format

The answer that mattered was separating the two. Turtle is now an **export and
import format alongside JSON**; JSON stays the wire format between browser and
API, and Neo4j stays the store. Two specific reasons, not general caution:

**RDF has no inherent ordering.** `:a skos:narrower :b, :c` is a *set*. Sibling
order became authoritative in Part 10 when the Node Manager gained the ability to
reorder, so a naive translation would have silently dropped it. Order is carried
explicitly in `fract:position`, and three separate tests assert it survives —
including one whose labels are deliberately reverse-alphabetical, so the assertion
cannot pass on sorting luck.

**Transient visual state is not ontology.** Positions and colours are recomputed
by the layout engine every frame, so they are not exported. A re-imported map is
laid out afresh. That makes the Turtle export deliberately narrower than the JSON
one, which is the right trade for an interchange format.

### 12.2 SKOS, not OWL

`skos:broader`/`skos:narrower` are *deliberately* vague about whether a child is a
subclass, a part, or simply a narrower idea — which is exactly what a mind map
means. OWL's `subClassOf` would force that decision on every single edge, and it
would be the wrong one about half the time.

```turtle
@prefix skos: <http://www.w3.org/2004/02/skos/core#>.
@prefix dcterms: <http://purl.org/dc/terms/>.
@prefix fract: <https://fractiverse.com/ns#>.
@prefix : <https://fractiverse.com/map/demo#>.

<https://fractiverse.com/map/demo> a skos:ConceptScheme;
    dcterms:title "My Ontology";
    skos:hasTopConcept :root.
:consciousness a skos:Concept;
    skos:prefLabel "Consciousness";
    dcterms:description "What recursion feels like from the inside";
    fract:tier 1;
    fract:tag "mind", "recursion";
    skos:broader :root;
    fract:position 0.
```

App-specific terms live in their own `fract:` namespace rather than squatting on
SKOS's. Unrecognised `fract:*` predicates are read back into metadata on import,
so a field a future version adds survives a round trip through this one.

`skos:narrower` is emitted as well as `skos:broader`, for readers that follow only
one direction — but on import **`broader` is authoritative** and `narrower` only
fills gaps. Treating them as equal would let a file contradict itself.

### 12.3 The library is lazy, and that is verified

N3 handles the parsing, because writing Turtle is easy and parsing it correctly is
not — prefixes, blank nodes, collections, escapes. It is loaded with a dynamic
`import()` so it is not in the initial bundle, and the browser check asserts the
`turtle` chunk is **not** requested on page load and **is** requested after
pressing Export.

### 12.4 The JSON export had never worked

Found while wiring the new buttons next to the old ones. `exportToCLI()`
serialised `nodeBridge.exportForCLI()`, which reads the CLI bridge's *own* node
collection — and that is only populated by the local Python helper. Measured on
the deployed build:

```
engine graph:  36 nodes
bridge export:  0 nodes
```

So **Export produced a valid JSON file containing zero nodes**, on every
deployment, for the entire life of the feature. Silently: a download that appears
to succeed, a file that opens fine, and nothing in it.

Both export paths now serialise `fractalityEngine.nodeGraph` — the graph actually
on screen. Import is one button that detects JSON or Turtle from the file's
contents rather than asking, since the user already has a file and asking only
invites the wrong answer. `FractalNode.toJSON()` happens to be shape-compatible
with `NodeGraph.fromJSON`, so an old CLI export still imports.

The browser check asserts the file's **contents** rather than that a download
happened — which is the distinction the original bug lived in. Mutation-checked:
restoring the bridge-based export reports `the JSON export contains ZERO nodes —
the original bug`.

### 12.5 Two bugs in the converter, both found by tests

- **Base IRI inference was poisoned by the ConceptScheme.** The scheme's IRI is
  the base minus its trailing `#`, so the longest-common-prefix calculation
  collapsed to `.../map/` and every id came out as `test#alpha` instead of
  `alpha`. Fixed by inferring the base from the concepts alone.
- **Untyped numeric literals came back as strings.** `0.5` was written without a
  datatype, making it `xsd:string`, so a round trip returned `"0.5"`. Integers had
  a datatype and were fine, which is why only one test caught it. Floats now get
  `xsd:double` and booleans `xsd:boolean`.

`tests/turtle.test.js` is 17 tests, and the ones that earned their place are the
awkward ones: ids containing spaces, slashes, `#` and non-ASCII; labels containing
quotes, newlines and backslashes; a foreign SKOS file using neither our base IRI
nor our terms; a file stating only `narrower`; a legal Turtle **cycle**, which is
detached with a warning rather than handed to a layout engine that assumes a tree.

### 12.6 render.yaml reconciled

It described only the static site; the API block was commented out, because the
API service was created by hand in the dashboard. Both services are now described.

The header now says the thing that was missing: **a Blueprint only governs services
Render created from a Blueprint.** Both live services were made by hand, so this
file is documentation — accurate documentation, but Render is not reading it, and
editing it changes nothing about the running deployment. It exists so a service
that is lost can be rebuilt without reconstructing its settings from memory.

Anything secret, or that only the dashboard knows, is `sync: false`. Hardcoding a
guessed API hostname would be worse than leaving it unset, because a Blueprint
sync would then overwrite a working value with a wrong one.

`plan: free` is recorded as what is actually running, with the trade-off written
down rather than asserted: a free instance spins down after ~15 minutes idle and
the next request waits ~50 seconds, and that hurts *more* at low traffic, not less
— a few people checking in daily means almost every visit is a cold start. The
note names the two conditions that should trigger an upgrade (chat existing, or
showing it to someone whose first impression matters) instead of the previous
blanket "not the free tier".

## Part 13 — Identity, and two bugs that were not what they looked like

A desktop testing session produced a list. Three items on it had causes other than
the obvious one, which is the interesting part.

### 13.1 "Maps saved on my phone don't show up on desktop"

Not a sync failure. The maps were in Neo4j the whole time.

Signing in had **no home of its own**. The only two ways to do it were a button
inside the Maps panel's header and one inside the feed composer. So a fresh desktop
browser was never signed in — and `MapsPanel.refresh()` branches on exactly that:

```js
const maps = signedIn ? await listMyMaps() : await listPublicMaps();
```

An anonymous visitor gets the public list. The maps in question were private, so
they were correctly absent. Reported as a sync problem because there is no way to
tell those two apart from the outside.

Fixed by giving identity a dock entry of its own — the first row of ☰ More, which
reads "Sign in" or "Account" depending on the session. `DockMenu` gained support
for callable labels to make that possible, re-resolved on every `refresh()` so the
label tracks the session without a rebuild (a rebuild closes any open sheet).

### 13.2 "The dock disappears when Cone View is selected"

Overlay stacking. The Cone view is `z-index: 900` across the whole viewport; the
dock was `z-index: 30`.

The cone's height was written as `bottom: var(--dock-height)`, which clears a
**bottom**-anchored dock. On a desktop the dock is at the **top**, where
`--dock-height` is 0 — so the cone covered it completely, and the only way back
was a page refresh.

Two changes, because either alone would have been fragile:

- The dock is now `z-index: 1200`. Navigation should outrank the things it
  navigates to, as a rule and not as a special case for this overlay.
- `--dock-top-height` joins `--dock-height`, and exactly one of the two is non-zero.
  Full-screen overlays inset from both, so they clear the dock at whichever edge it
  happens to be on.

### 13.3 "Cone view doesn't recognise name changes made in Node Manager"

The most instructive one, because **the cone was never showing stale data**.

Instrumenting `fillText` proved renamed labels were painted and old ones were not.
My first reading of that instrumentation was wrong in a way worth recording: it
counted a `Set` of painted *strings* and found 21 for 36 nodes, which I took for
"15 nodes are never labelled". The test data simply reuses labels — 36 nodes carry
21 distinct names. Measured by node id instead, every node was reachable.

The real cause is that a label was only drawn for a node on the **focused tier**
whose `nearness > 0.45` — the front third of one ring. Renaming a node and coming
to the cone to look at it therefore showed nothing, unless that node happened to be
on the focused tier and facing the viewer. Indistinguishable from the cone ignoring
the edit; the new name simply had nowhere to appear.

Two fixes:

- **The readout always names the selected node.** Select it anywhere — the Node
  Manager, the 3D view, a tap in the cone — and its current name is on screen.
  This is the one that closes the reported loop.
- **Labels are placed with collision testing** rather than an arc cutoff, so the
  whole focused tier is labelled and only genuinely overlapping text is dropped.
  The selected node is placed first, so it never loses a collision.

The general lesson: "it is not picking up my change" and "my change has nowhere to
be seen" are the same report, and only one of them is a data bug.

### 13.4 Feed posts were attributed to "Anonymous"

Clerk's session JWT carries no name. A default token has `sub`, `iss` and `exp`
and nothing else unless a custom JWT template is configured, so:

```python
username = claims.get("username") or claims.get("name")   # both absent -> None
```

The display name has to live somewhere this API can read, which means the User
node. `GET /me` and `PATCH /me` were added, and the pulse queries now prefer
`display_name` over the provider's `username`.

The frontend seeds it once from Clerk's client (which *does* know the name), and
**only when no name has been set** — so a name the user chose is never overwritten
by the provider's on a later sign-in.

`PATCH /me` distinguishes an omitted field from an explicit null. That is not
pedantry: collapse them and an avatar can be set but never removed. Two tests
assert the distinction directly.

### 13.5 Map visibility had no control at all

Every map was created private and there was no way to publish one, which made
"sharing" mean share links exclusively.

A cycling button — 🔒 Private → 🔗 Link only → 🌍 Public — because the three states
have a natural order and it is one tap either way. `unlisted` sits in the middle
deliberately: it is not a lesser `public` but "not listed, readable with a link",
which is the state a share link is for.

Publishing asks for confirmation and un-publishing does not. Making something
visible to strangers is the step that cannot be taken back for anyone who has
already looked.

### 13.6 Editing your own posts

`PATCH /pulses/{id}`, with ownership in the Cypher `MATCH` so it cannot reach
another author's post and there is no window between checking and writing.

Every edit stamps `edited_at`, and the card shows an "edited" badge. A feed where
posts can be silently rewritten after people have responded to them is worse than
one without editing at all.

The edit model reuses `PulseCreate`'s validators by construction rather than by
copying them, so a link refused on the way in cannot become acceptable on an edit.
There is a test for exactly that.

### 13.7 Coverage

`api/tests/test_profile_and_edits.py` — 16 tests, weighted toward the two things
that fail silently: PATCH semantics (omitted vs null) and edit authorization.

`npm run browser-check` gained an "identity and overlays" section: that the dock
exposes an identity entry, that the account panel opens and states what is
available, that the dock stays reachable with the Cone view open, that the cone
does not overlap it, that the readout names the selected node, and that visibility
cycles and can reach public.

## Appendix — Preventing recurrence

`npm run health` checks for the specific failure modes documented above:

| Check | Catches |
|---|---|
| ESM parse of every JS file | escaped template literals, stray braces, truncation |
| `py_compile` of every Python file | merged lines, bad identifiers, indentation |
| Relative import resolution | modules that were never created, moved files |
| HTML `src`/`href` resolution | broken stylesheet and script links |
| Bare imports vs `package.json` | undeclared dependencies |
| Named imports vs target's exports | `import { x }` where the module never exported `x` |
| `\`` detection | template literals pasted escaped |
| ~20,000-byte file size | chat-window truncation |
| `def init(self` in Python | dunders eaten by a Markdown renderer |
| Contested layout declarations | one selector positioned from two stylesheets |

It exits non-zero on any error, so it can gate CI. It reads files, though — for
anything about whether the app is *usable*, see `npm run browser-check` and
Part 6.7. Comments are blanked before
the import scan so example code inside `/* */` is not reported — the naive
version produced two false positives on this repo.

**One practical habit** avoids nearly everything in Part 1: when copying code
out of a chat, use the code block's copy button rather than selecting rendered
text, and check the byte count of anything that lands near 20 kB.
