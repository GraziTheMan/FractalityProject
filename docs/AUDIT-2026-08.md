# Fractality Platform — Full Codebase Audit

**Date:** 2026-08-17
**Audited version:** v0.13.0 (commit `f83fec7`) → v0.13.1
**Scope:** the whole repository — 264 files, ~74k lines of JavaScript, 35 Python modules

---

## Executive summary

Before this audit, **the application could not be built, served, or loaded.**
Not "had bugs" — it could not start. Ten JavaScript files did not parse, five
Python modules did not compile, the package manifest contradicted every source
file in the repo, and the single line responsible for booting the 3D engine
called a method that did not exist.

After this audit the project builds, boots in a browser with zero console
errors, renders its 36-node test graph at interactive frame rates, and has a
test suite and a repeatable health check.

| | Before | After |
|---|---|---|
| JS files that parse | 95 / 105 | **all** |
| Python files that compile | 30 / 35 | **all except one archived file** |
| Unresolved relative imports | 40 | **0** outside `archive/` |
| Broken HTML asset references | 18 | **0** outside `archive/` |
| `npm run build` | did not exist | **succeeds** |
| Page loads without JS errors | no | **yes** |
| Automated tests | 3 empty placeholder files | **238 JS + 420 API + 57 live-DB integration** (44 / 66 / 16 at the original audit date; the parts below added the rest) |

The single most useful finding is not any individual bug but the **cause**: the
overwhelming majority of defects trace to a handful of mechanical copy-paste
failure modes, each with a recognisable signature. Those signatures are now
encoded in `scripts/health-check.mjs`, so they cannot silently recur.

## Part 1 — Root causes

Rather than 60 unrelated bugs, this was five repeated mistakes.

### 1.1 Truncation at a copy limit (3 files, ~15 methods lost)

Three files were **exactly** 20,000 / 20,004 / 20,028 bytes and ended
mid-identifier:

```js
siblingEl.dataset.nodeId = node.s          // NodeInfoPanel.js, cut here
const audioAgent = this.agentNetwork.getNode('age   // FractalAIPrototype.js
import { Consciousn                        // ConsciousnessNode.js
```

A file ending mid-token at a round 20,000 bytes is not a coding error, it is a
chat window's copy ceiling. Two more files (`data-console.html` at 20,011 and
`DebugShell.html` at 20,039) share the signature and are still truncated in
`archive/`.

**What was lost.** `NodeInfoPanel.js` lost nine methods —
`_onTreeNodeClick`, `_navigateToNode`, `_expandNode`, `togglePin`,
`_setupEventListeners`, `_animateOpacity`, `_getScoreColor`,
`_getRelationshipLabel`, `_formatValue` — every one of them called from the
surviving code. `FractalAIPrototype.js` lost six.

**Fixed** by completing the cut method and reconstructing the missing ones
against their existing call sites. Navigation follows the `nodeSelected` window
event that `SearchInterface` already used, so the restored code matches the
project's own convention rather than inventing a new one.

### 1.2 Markdown rendering ate the source (5 Python files)

The clearest single diagnosis in the audit. Three `core/field_engines/` modules
contained **zero** occurrences of `__init__`, while their working sibling
`superionic_database_enhanced.py` contained four. The damage:

| Original | As committed |
|---|---|
| `def __init__(self):` | `def init(self):` |
| `if __name__ == "__main__":` | `if name == "main":` |
| `"""docstring"""` | bare text |
| `# comment` | bare text |
| two lines | one merged line |

Double underscores are Markdown's bold/italic markers. This code was pasted
from *rendered* Markdown, not from a code block — which also explains the
collapsed newlines (rendered paragraphs) and the stripped `"""` and `#`.

```python
# What was committed:
class OntologyGraph: def init(self): self.nodes = {} self.edges = defaultdict(list)

# What it had to be:
class OntologyGraph:
    def __init__(self):
        self.nodes = {}
        self.edges = defaultdict(list)
```

**Fixed** by reconstructing all five files. `field_glyph_generator.py` and
`superionic_database.py` were then run to confirm they produce correct output.

### 1.3 Multi-file AI responses pasted into one file (2 files)

When an assistant emits several files in one reply, the separators say where
each belongs. Those separators were pasted along with the code:

```js
// ===========================
// src/core/EventBus.js          ← this is a filename, not a comment
// Central event system
export class EventBus { ... }
```

`src/mobile/MobileApp.js` was **five** modules concatenated, and it imported
`EventBus`, `MobileConfig`, `HapticFeedback` and `AnimationEngine` from paths
that did not exist *while also defining all four in its own body* — plus, at
line 504, an import of itself. It failed to parse on
`Identifier 'EventBus' has already been declared`.

`src/ecs/ECS.js` had the same shape: it exported nothing at all, ran a demo
world at import time, and `main.js` imported `./ecs/components.js` and
`./ecs/systems/*.js` — the exact split the file's own comments described.

**Fixed** by splitting both at their separators, into the paths those
separators named.

### 1.4 Escaped template literals (4 files)

```js
this.root.innerHTML = \`
  <div class="menu-actions \${this.open ? 'open' : ''}">
```

`\`` and `\${` are what you get when a template literal is nested inside
another template literal and the outer layer is stripped. Four `ui/` modules
were unparseable because of it.

### 1.5 Divergent duplicates, where the *stale* copy was live

Four `main.js` files, two `index.html`, five `package.json`. The dangerous case
was not the duplication but which copy won:

- `public/components/radialMenu.js` (live) **lacked `setHandedness()`**.
  `mirrorToggle.js` calls it on every Mirror click, so the button threw a
  `TypeError`. The *archived* copy still had the method — the older file was the
  more complete one.
- `public/index.html` linked `./src/styles/main.css`, a path that only resolves
  from the repository root. It had been moved *into* `public/`, breaking all
  three stylesheet links.

## Part 2 — Findings that were not copy-paste damage

### 2.1 SECURITY: AI provider keys in browser code

**Severity: high.** `src/chat/FractalityChat.js` runs client-side and did this:

```js
this.apis = {
    claude: new Anthropic({ apiKey: config.claudeKey }),
    gpt: new OpenAI({ apiKey: config.openaiKey }),
    ...
```

fed from `src/config/chatConfig.js`:

```js
claudeKey: process.env.ANTHROPIC_API_KEY || 'your-claude-api-key',
```

Two independent problems:

1. **`process.env` does not exist in a browser bundle.** Reading it throws a
   `ReferenceError` at module load. So this code could never have run.
2. **Had it "worked", it would have been worse.** Any key reachable from client
   code is bundled into the JS served to every visitor, readable in devtools,
   and spendable against your quota.

**Action taken:** the key fields are now explicitly empty, with the reasoning
documented in place, and `chatConfig` reads an optional `VITE_AI_PROXY_URL`
instead. `FractalityChat` throws a clear error naming the missing credentials
rather than constructing SDK clients with `undefined`.

**Still outstanding:** the actual fix is a server-side proxy. `server.js` is the
natural home — it can hold real keys in its own environment. Until that exists
the chat module is intentionally not importable, and its three SDKs are
deliberately absent from `package.json`.

### 2.2 The packaging manifest contradicted the entire codebase

`package.json` declared `"type": "commonjs"` with dependencies of exactly
`express`, `socket.io` and `url`. Meanwhile:

- every file in `src/` is an ES module
- `src/` imports `three`, which was **not a dependency**
- `vite.config.js` existed, and `vite` was **not a dependency**
- `vite.config.js` pointed at `./index.html`, which **did not exist** (it was in `public/`)
- `server.js` served `__dirname` and fell back to a root `index.html`, so in
  production **every route 404'd**
- `server.js` had an explicit `/chat` route serving a `chat.html` that lives in the archive
- four *other* `package.json` files disagreed about name, version and module type

`render.yaml` compounded it: `buildCommand: npm install` with no build step, so
the deployed site would have served raw ES modules containing a bare `three`
import that no browser can resolve.

**Fixed.** One manifest, `type: module`, `three` + `vite` declared, real
scripts. `server.js` converted to ESM, serves `dist/` when built and warns when
not. `render.yaml` now builds. The four duplicate manifests are gone.

### 2.3 Modules imported but never written (3 files)

Not damage — code written against modules that were never created:

| Missing module | Imported by | Resolution |
|---|---|---|
| `src/intelligence/ResonanceEngine.js` | `MobileApp`, `ResonanceFeedController` | Implemented, local-only |
| `src/visualization/ParticleFieldRenderer.js` | `MobileApp` | Implemented, canvas-2D |
| `core/agent_systems/ExecutiveAgent.js` | `scripts/test_loop.js` | Implemented |
| `core/field_engines/phase_engine.py` | `consciousness_user.py` (×2 methods) | Implemented |

Each was written against the API its callers already assumed — method names,
arguments and return shapes were all recoverable from the call sites.

`phase_engine.py` is worth a note. `ConsciousnessUser` already declared
`LIQUID_THRESHOLD = 200.0  # Energy * frequency` and
`SUPERIONIC_THRESHOLD = 50000.0`. Taken literally, a brand-new user
(energy 100 × frequency 432 = 43,200) would classify as LIQUID immediately —
yet the enum documents `SOLID` as *"New users, fixed patterns"*. Driving phase
from the frequency **gain** over the 432 Hz baseline makes every threshold land
correctly: a new user has gain 0 → SOLID, and 100 × 500 Hz = 50,000 → SUPERIONIC.
The thresholds are read from the user class rather than duplicated.

### 2.4 A dead loader, and `THREE` undefined in four modules

`FractalityEngine`, `FractalityRenderer`, `AnimationSystem` and
`EnergyVisualizer` all began with:

```js
import { loadThreeJS, getEnvironmentInfo } from '../utils/ThreeJSLoader.js';
```

…and **never called either function**, then used a bare `THREE` that was
therefore always `undefined`. `ConsciousnessNode.js` used `THREE` 18 times with
no import at all.

The loader itself could not have helped: it is async and returns `{ THREE }`,
but every consumer used `THREE` synchronously in its constructor. It was also
the source of Vite's "dynamic import cannot be analyzed" warning.

**Fixed** with a static `import * as THREE from 'three'` in all five, which the
bundler resolves and tree-shakes. `ThreeJSLoader.js` is retained but is no
longer on the critical path.

### 2.5 The bug that kept the visualizer dark

`src/utils/appState.js` was nine lines:

```js
export const AppState = {
  currentView: 'bubble',
  setView(view) {
    const content = document.getElementById('content-view');
    content.innerHTML = `<div ...>Switched to: <strong>${view}</strong></div>`;
  }
};
```

But all three `main.js` variants contain:

```js
AppState.on('viewChanged', async (view) => {
  if (view === 'bubble' && !fractalityEngine) {
    fractalityEngine = new FractalityEngine('fractality-canvas');
    ...
```

`AppState` has no `on`. That line — the one responsible for constructing the
engine, loading data and starting the render loop — threw
`TypeError: AppState.on is not a function` and aborted the rest of module
initialisation. **The 3D visualizer had never run.**

A second bug hid behind it: `setView` overwrote `#content-view`'s `innerHTML`,
and `#fractality-canvas` is a child of `#content-view`. Any view switch would
have destroyed the canvas the renderer holds a reference to.

**Fixed.** `AppState` now has a real `on`/`off`/`emit` (async-aware, with
per-handler error isolation), placeholder text renders into its own element so
the canvas survives, and `main.js` sets an initial view so something is on
screen at load.

### 2.6 Neither stylesheet styled the actual page

`index.html` declares `#radial-menu`, `#state-indicator`, `#mirror-toggle`,
`#content-view`, `#biometric-panel`. But `main.css` styles `#canvas`,
`#ui-overlay`, `#controls` — an older DOM — and `mobile-menu.css` styles
`#menu-root`, `#menu-container` — `MenuController`'s DOM. Of the shell's
elements, only `#desktop-dock` had any rules.

The visible consequence: `#radial-menu` had no dimensions, so
`getBoundingClientRect()` returned ~0 and `RadialMenu.render()` stacked all
nine buttons on one point.

**Fixed** with `src/styles/shell.css`, matching the existing cyan-on-black
conventions. `RadialMenu` now also clamps its radii to its container and
re-lays-out on resize, so the fan is responsive instead of clipped.

### 2.7 Assorted correctness bugs

- `TriadicConsciousnessEngine` instantiated `SharedConsciousContext` **without
  importing it** — constructing the engine threw `ReferenceError`. Now tested.
- `main.js` called `testGenerator.generatePattern()`; the method is
  `generateTestPattern()`. Further, `'golden'` was not one of its cases despite
  `generateGoldenSpiral()` existing, so it would have silently fallen through
  to `default` and returned the trivial graph. Added `golden`/`spiral`/
  `balanced`/`organic` so the five patterns the README advertises are reachable.
- `def 8x8x8_cube_preparation` — a Python identifier cannot begin with a digit.
- `core/field_engines/superioronic_database.py` was misspelled ("superi-**ro**-onic").
  Two modules do `from superionic_database import SuperionicDatabase`, so they
  could never have imported it. Renaming fixed all three at once.
- `graph-chat-sync.js` imported `./init.js`; the file is at `src/main/init.js`,
  and it did not export `nodeGraph`.
- `FractalityRenderer` set `outputEncoding`/`sRGBEncoding`, removed in three r152+.
- `consciousness_backend/requirements.txt` was **empty** (2 bytes). Reconstructed
  from actual imports across the Python tree — 16 packages.
- `MainMenuRadial.js` used `assert { type: 'json' }`, a withdrawn proposal.
- The ECS ran a second uncapped `requestAnimationFrame` loop at a hardcoded
  1/60 delta. Now uses real elapsed time and pauses on tab hide.
- `MenuController.destroy()` calls `this.eventBus.off('node:focus')` with no
  handler argument, which is a silent no-op — listeners leak. **Not fixed**;
  flagged below.

### 2.8 Dead weight removed

- `transfer/` — a 25-byte `<!-- Placeholder HTML -->` and a 2-line manifest
- `json/` — two stale `package.json` copies parked in a folder named `json`
- `server/` — a stale manifest, an empty `start.md`, and a README byte-identical

## Part 5 — Follow-up: deployment preparation

A second pass, done while preparing the app to deploy at fractiverse.com as a
static site. It turned up four more defects, two of them security-relevant.

### 5.1 A second place shipping API keys to the browser

§2.1 covered `src/chat/`. `src/mobile/chat-ai-hub.js` was doing the same thing
independently and had been missed:

```js
export async function initAIBot(openaiKey) {
  const resp = await fetch('https://api.openai.com/v1/chat/completions', {
    headers: { 'Authorization': `Bearer ${openaiKey}` },
```

A raw OpenAI key, passed into client code, sent from the browser. Rewritten to
call a server-side proxy (`VITE_AI_PROXY_URL`) and to stay disabled until one is
configured. **Lesson for the audit itself:** finding one instance of a pattern is
a reason to grep for the pattern, not to close the finding.

### 5.2 Stored XSS in the feed renderer

`ResonanceFeedController._createPulseElement()` built markup with `innerHTML`
and interpolated `pulse.title`, `pulse.preview`, `author.name`, tags and
`media.url` **unescaped**. Harmless while the feed is seeded locally; the moment
strangers can post, a single title containing `<img src=x onerror=...>` executes
in every reader's browser.

Fixed by escaping every user-authored value and validating URLs through a new
`src/utils/sanitize.js` (`escapeHtml`, `safeUrl`, `safeCssValue`). `safeUrl`
rejects `javascript:`/`data:` schemes including control-character obfuscation
(`java\nscript:`), which a naive `startsWith` check misses. 12 tests cover the
payloads.

This is the highest-priority finding for the stated goal of a public social
feed. Note it is a *mitigation*, not a solution: the renderer still uses
`innerHTML`. Server-side validation is still required, and moving that renderer
to DOM construction would remove the class of bug entirely.

### 5.3 Named imports that resolved to `undefined`

Two files imported names their target never exported:

- `chat-ai-hub.js` imported `{ chatSocket }` from `chat-client.js`, which only
  exported `initChatUI`.
- `chat-ui.js` imported `{ initChatUI }` **from itself** — the same snippet had
  been pasted into both it and `mobile-ui.js`.

Both resolved to a real file, so the original health check passed them. It now
parses each module's exports and verifies named imports against them; verified
by deliberately breaking an import and confirming a non-zero exit.

### 5.4 Deploy-hostile hardcoded hosts

- `NodeBridge` hardcoded `http://localhost:8001` and probed it on every page
  load. On a deployed site that is unreachable, and on HTTPS it is blocked
  outright as mixed content — a guaranteed failed request for every visitor.
- `chat-client.js` hardcoded `https://thefractalityplatform.onrender.com`, a
  previous deployment, so any new deploy would have talked to the old one. It
  also opened the socket at *module import* time and loaded socket.io from a
  CDN.

Both now read from `src/config/deploy.js`, the single source for
environment-derived config. The CLI bridge defaults to localhost during `vite
dev` only; chat is disabled unless `VITE_SOCKET_URL` is set; socket.io-client
comes from npm via a dynamic import, so it is code-split out of the main bundle
(confirmed: 0 occurrences in `main-*.js`).

**Verified:** the production build now loads with **zero page errors and zero
failed network requests**, while `vite dev` still probes the CLI bridge, so the
local CLI workflow is intact.

### 5.5 The Cypher is now verified

The caveat that ran through Parts 3 and 4 — that `api/repository.py` had never
touched a real database — is closed. All 16 integration tests pass against a live
AuraDB Free instance in 32s.

Getting there took three fixes, two of them mine, and the run was worth it:

1. **A hardcoded database name.** `settings.neo4j_database` defaulted to `"neo4j"`
   and was passed explicitly to every session. Aura names the database after the
   **instance ID** (`1efeea86`), so every query failed with `DatabaseNotFound`.
   Now defaults to empty, meaning "let the server resolve its default".
2. **A `/health` endpoint that lied.** `verify_connectivity()` only proves the
   server answered; it does not check the database exists. The API booted cleanly
   and reported `{"database": "ok"}` for a service that could not serve one
   request. Health now runs a real query. Relatedly `apply_schema()` logged seven
   warnings and returned `0`, which reads as success to a caller not checking the
   count — it now raises when everything fails.
3. **Integration tests that could not pass.** The `driver` fixture was
   module-scoped while pytest-asyncio gives each test its own event loop, so the
   driver held sockets bound to a dead loop. Every test failed with "Future
   attached to a different loop" regardless of the database. Now function-scoped.

An assumption I asserted as fact and got wrong: current AuraDB issues the
**instance ID as the username**, not `neo4j`, and spells the variable
`NEO4J_USERNAME`. The diagnostic script actively warned users toward the wrong
value. Corrected, and `scripts/check_neo4j.py` now exists to give a one-line
diagnosis instead of a driver traceback.

One cosmetic wart: `deploy.js` reads env vars through a helper function, so Vite
cannot statically replace `import.meta.env.DEV`, and the string
`http://localhost:8001` remains in the bundle as dead weight (~25 bytes). The
runtime behaviour is correct; the literal is never used in production.

## Part 6 — Follow-up: mobile was unusable

Reported after the first deploy went live: *"on mobile it's too cluttered to be
able to do much of anything. I had to orient my phone in landscape to be able to
see the maps button."*

The landscape detail is the diagnosis. A phone in landscape is 844px wide, which
clears the 720px breakpoint — so the layout that worked was the **desktop** one,
and the mobile layout was the broken one.

### 6.1 The dock was hidden on exactly the devices that needed it

`index.html` marks the dock `class="desktop-dock desktop-only"`, and
`shell.css` had:

```css
@media (max-width: 720px) { .desktop-only { display: none !important; } }
```

So on a phone in portrait, **Maps, Search, Debug, Export and Import were all
absent from the page** — not small, not covered, gone. The comment justifying it
said the radial menu was the primary navigation on narrow screens, which was
true of the menu and false of everything the dock held.

A second defect in the same rule set would have collapsed the dock even if it
had been shown:

```css
max-width: min(760px, calc(100vw - 420px));   /* -30px on a 390px screen */
```

A negative `max-width` collapses the element to nothing.

The dock is now a bottom bar below 720px: fixed to the bottom edge, one
horizontally-scrollable row, `env(safe-area-inset-bottom)` padding for the home
indicator, and emoji-only labels — six labelled buttons need about three screen
widths, six glyphs need 280px.

`--dock-height` in `shell.css` is now the single number every bottom-anchored
element measures from (0 on desktop, where the dock sits at the top). Previously
`NodeInfoPanel`, `NodeDebugPanel`, the mirror toggle and the home button each
hardcoded `bottom: 20px`, i.e. underneath wherever the dock ended up.

### 6.2 The breakpoint needed a height test, not just a width one

Fixing width alone left landscape phones on the desktop layout, where the dock
wrapped to two rows and the 364px-tall performance overlay filled a 390px-tall
screen. The compact layout now triggers on `(max-width: 720px), (max-height:
500px)`, and `PerformanceDashboard._isNarrowScreen()` applies the same test so
CSS and JS cannot disagree.

### 6.3 The radial menu's own layout was wrong, not just cramped

`RadialMenu.render()` spaced its nine items by equal **angle** across a
180-degree arc. Near the poles of an ellipse `sin()` flattens out, so the
outermost pair ended up ~13px apart vertically while the chips are ~35px tall.
The visible result on a phone: `🧠 Mindmap` rendered underneath `👥 Social`.

Shrinking the fan to fit the screen made it worse, because the gap is
`(height - 48) / 8`.

It now distributes items by equal **vertical** spacing, tracing the same ellipse
parameterised by y instead of by angle. The gap is `2 * radiusY / (count - 1)`
everywhere, so whether the labels fit is a property of the box rather than of
which end of the fan you look at. `radiusX` is also clamped against the
*measured* width of the widest label instead of a guessed 56px margin.

This is a fix to the existing component, not the replacement in item 3 below —
that is still outstanding and still the agreed direction.

### 6.4 The node info panel could never appear on a phone

`FractalityEngine` showed it from `_handleMouseMove` only. There is no
`mousemove` on a touch screen, so tapping a node focused it and showed nothing.

Three things had to change together:

- `_handleClick` now shows the panel too (`touchstart` already routes there).
- `show(node, { immediate: true })` skips the hover delay. Without that the
  tap-synthesised `mousemove` — which fires *before* `click` — lands on empty
  space, calls `hide()`, and cancels the pending show.
- The panel is **sticky** once opened by a deliberate tap, since there is no
  pointer-out event to close it, and it gained a **✕ button**. It had only a pin
  button, so on touch it would have appeared once and then covered the bottom of
  the screen permanently.

The close glyph is `U+00D7`, not the heavier `U+2715`: the latter is missing from
some Android and Linux font stacks and renders as an empty box, which for a close
button means the panel looks impossible to dismiss. That was caught in a
screenshot, not in the DOM.

### 6.5 Clicking a node silently stopped working — the real "pyramid" bug

Found while testing the above, and the most consequential item here.

`THREE.InstancedMesh.raycast()` rejects a ray outright if it misses
`this.boundingSphere`, and computes that sphere exactly once — on the first
raycast — then caches it forever. The instances in this app move every frame
(layout, animation, focus changes), and `_setGeometry()` swaps
`instancedMesh.geometry` on every quality change without invalidating anything.

So after the layout drifted, or after adaptive quality switched to low-poly,
**clicking or tapping a bubble did nothing at all**: no selection, no panel, no
error in the console. The renderer now nulls `boundingSphere` and `boundingBox`
after each matrix update and on every geometry swap, which makes `raycast()`
recompute on demand — one pass over the visible instances, and only on a real
pointer event.

This is very likely part of what was reported a year ago as *"the bubbles turn
into pyramids when I click anything and don't turn back."* The pyramids
themselves were §2.5's geometry-swap bug; the unresponsiveness afterwards was
this.

### 6.6 Smaller things in the same pass

- **The Search dock button called `show()`, never `hide()`.** Pressing it twice
  reopened an already-open panel. Escape and ✕ covered it on desktop; on a phone
  the panel then sat over the canvas absorbing taps meant for the map.
  `SearchInterface.toggle()` added.
- **`FractalityEngine.togglePerformanceMonitor()` had no caller anywhere.** The
  overlay was on by default with no way to dismiss it. It now defaults off on
  compact screens and has a `📈` dock button.
- **The CLI bridge controls were dead weight in production.** `hasCliBridge()`
  existed and was never called, so a deployed phone showed an Auto-Sync button
  that could only fail, a permanently-red "CLI Disconnected" light, and a
  5-second polling timer with nothing to poll. All three are now conditional.
  Export/Import stay — they are file download/upload and work anywhere.
- **`fractalityEngine.navigateToNode()` does not exist.** The method is
  `setFocus()`. Both call sites in `main.js` threw a `TypeError`, which means
  clicking a search result and pressing "Navigate Here" had never worked.
- **`.perf-dashboard.hidden` only set `opacity: 0`**, leaving an invisible
  overlay eating touches. It happened to work because `shell.css` forces
  `display: none` on `.hidden` globally — a panel should not depend on another
  stylesheet for that.
- **Notification toasts** were anchored right with no left bound, so a long
  message ran off the side of a phone.
- **`MapsPanel._describe()`** rendered a failed cross-origin fetch as the raw
  browser string `Failed to fetch`. On Render's free tier that is almost always
  a cold start, so it now says so and points at the refresh button. Matched by
  error *shape*, since the message differs per browser (Chrome "Failed to fetch",
  Safari "Load failed", Firefox "NetworkError when attempting to...").

### 6.7 Why none of this was caught earlier

Every item above is invisible to `npm run health`, which parses files. Each one
needed a browser at a phone viewport, and two of them needed a *screenshot*
specifically — the overlapping menu labels and the blank close button were both
perfectly well-formed DOM.

`npm run browser-check` (`scripts/browser-check.mjs`) now covers this. It drives
the built site in Chromium at 390x844, 844x390 and 1440x900 and asserts:

| Check | Catches |
|---|---|
| `elementFromPoint` on every control | elements present but covered, zero-size, or off screen |
| pairwise rect intersection of menu items | overlapping labels |
| `documentElement.scrollWidth > innerWidth` | horizontal overflow |
| second press on each dock button | panels that open but cannot be closed |
| real `touchscreen.tap` on a raycast-located node | touch paths that only work with a mouse |
| controls after `scrollIntoView` | actions stranded below a scroll fold |
| `setQuality()` across the hysteresis band | geometry that changes one way only |
| raycast after a geometry swap | stale `InstancedMesh` bounds |
| `pageerror` | uncaught exceptions on load or interaction |

Verified to gate: reinstating the `display: none !important` rule makes it
report six unreachable dock buttons and exit 1.

Playwright is deliberately **not** in `package.json` — it pulls a browser
download that every deploy would pay for. The script skips with instructions
when it is absent, and `npm run health` records that choice as a note rather
than a warning.

## Part 7 — Follow-up: a save that worked looked like a save that failed

Reported from a phone, with a screenshot: signed in, `💾 Save current` worked,
and the panel then read **"Could not reach the server"** with an empty list and
no visible way to share anything.

### 7.1 Reading the screenshot

`saveCurrent()` ends with `await this.refresh()`. So the sequence was: the write
succeeded, and the list request **immediately after it** failed at the transport
layer. That rules out the explanation the message was offering — a server that
had just accepted a POST is not cold-starting.

Three separate defects combined to produce that screen.

### 7.2 A committed save was reported as a failure

`refresh()` writes its own error into the status line, so its failure erased the
`Saved "…"` message that had just been written. The user is told their save
failed when the data is safely in Neo4j — the worst possible direction for this
error to lean, because the natural response is to try again and create
duplicates.

Writes now report through `_refreshAfterWrite()`, which keeps both facts:

> Saved "My Mind Map" — your map is saved. Press 🔗 Share for its link. The list
> could not be reloaded: …

`refresh()` returns `{ ok, message }` rather than only painting a status, so a
caller can tell what happened instead of inferring it from CSS classes.

### 7.3 Share existed only inside a list row

The only Share button was rendered per-map in `_renderList()`. When the list
request fails there are no rows, so there is no Share button — the control was
missing in precisely the situation where the user most needs it, which is why
the answer to "how do I share it" was "you cannot".

The map is known at that point: `saveCurrent()` sets `this.currentMap`. Sharing
never needed the list. There is now a `🔗 Share` button in the panel's action
row that acts on the current map, disabled only when there is genuinely nothing
loaded. All assignments to `currentMap` go through `_setCurrentMap()` so the
button cannot drift out of sync with what it would act on.

### 7.4 One transport hiccup was a hard failure

A single failed `fetch` ended the operation. A Render instance that is cold,
restarting, or was just killed refuses connections for a few seconds — worth
waiting out rather than reporting as a dead server.

`_request()` now retries transport failures with backoff (1.5s, 3s). The
important restriction:

**Only reads are retried.** `fetch` rejecting does not mean the server did not
process the request — the response may simply have been lost. Retrying a
`createMap` would create two maps. Writes get `retries = 0` and fail loudly.
There is a test for this, and it is mutation-checked: making writes retryable
makes it fail.

### 7.5 The error message asserted a cause it could not know

The previous wording blamed idle wake-up. The browser deliberately withholds the
reason for a failed cross-origin fetch, and cold start, a restart, a dropped
connection and **a CORS rejection** are indistinguishable from JavaScript.

So the panel now finds out instead of guessing. On a transport failure it probes
`/health`, which needs no auth and touches no data:

| `/health` | Conclusion shown |
|---|---|
| no answer | the service is down or restarting — check the logs |
| answers, `database`/`auth` not ok | up but not ready, naming which |
| answers, everything ok | this request specifically was blocked; the usual cause is CORS, and `CORS_ORIGIN` must list this exact origin |

That last row is the useful one, and it is the most likely explanation for the
reported screenshot: `/maps` is a *credentialed* cross-origin request, so it
fails wholesale if the API's `CORS_ORIGIN` does not match the site's origin
exactly — scheme, host and `www.` included.

One bug of mine surfaced while testing this: `_diagnose()` was not awaited, so it
resolved *after* `_refreshAfterWrite()` had written its status and silently
overwrote it — the "your map is saved" reassurance was replaced by the CORS
diagnosis. It now returns text for the caller to place, so the two cannot race.

### 7.6 The diagnosis itself was wrong

The first version of §7.5 shipped with a flaw that showed up immediately: on the
next report the panel said *"The API is not reachable at all — /health does not
answer either"*, while the owner noted they had only listed the `www` origin in
`CORS_ORIGIN`. Those two statements are inconsistent, and the panel was the one
that was wrong.

`checkHealth()` goes through `_request()`, which attaches an `Authorization`
header whenever someone is signed in. That makes it a **credentialed
cross-origin request**, so a CORS misconfiguration blocks `/health` exactly as it
blocks `/maps`. Using it to decide whether the server is alive is circular: it
cannot report on a failure mode that also suppresses it.

Worse, no ordinary `fetch` can settle this. Even without the auth header the
response still needs `Access-Control-Allow-Origin` before JavaScript may read
it, so "server gone" and "server fine, CORS blocking" are the same `TypeError`.

`MindMapClient.probeReachable()` resolves it with `mode: 'no-cors'`. That still
sends the request; it only makes the response opaque, so status and body cannot
be read. Which is enough — the promise **resolves** when a server answered and
**rejects** when no connection could be made:

| readable `/health` | `no-cors` probe | Conclusion |
|---|---|---|
| answers | — | up; report any `database`/`auth` problems it names |
| fails | resolves | **up, and CORS is blocking** |
| fails | rejects | genuinely down, restarting, or wrong URL |

It deliberately sends no headers: any non-safelisted header would take the
request back out of no-cors mode and reintroduce the failure it exists to see
past. There is a test asserting that.

When it is CORS, the message now names the origin to allow by reading
`window.location.origin` from the page — which removes the guesswork that caused
this in the first place, since `https://www.fractiverse.com` and
`https://fractiverse.com` are different origins and only one of them was listed.

Mutation-checked: replacing the probe with `const reachable = false` makes the
browser check report the exact wrong message that was on the owner's screen.

### 7.7 Coverage

`tests/mindMapClient.test.js` (9 tests) covers the transport layer: per-browser
error shapes, retry counts, that HTTP errors are never retried, that writes are
never retried, and that `checkHealth()` distinguishes unreachable from
up-but-broken.

`npm run browser-check` gained two sections. The first stubs the API into exactly
the reported state — POST succeeds, GET fails at the transport layer, `/health`
answers — and asserts the save is not reported as an error, that both facts
survive in the status, that Share works without the list, that the read was
retried twice, and that **the write was sent exactly once**. The second drives
the two indistinguishable failures (CORS blocking versus nothing listening) and
asserts each produces its own diagnosis and not the other's, and that the CORS
message names the page's actual origin.

## Part 8 — CORS confirmed, and a toast styled from two places

### 8.1 The save/share loop is verified end to end

`CORS_ORIGIN` was listing only `https://www.fractiverse.com`. Adding both
origins fixed it:

```
CORS_ORIGIN = https://fractiverse.com,https://www.fractiverse.com
```

With that in place the owner confirmed the whole loop on a phone: save, list,
open, share, **and the share link opening for an anonymous visitor in an
incognito window.** That single path exercises Clerk auth, the Cypher in
`api/repository.py`, share-token authorization and the graph adapter together,
which is the check `docs/DEPLOYMENT.md` asks for. So the diagnostic added in
§7.6 was right, and the cause was the one it named.

### 8.2 The toast was 814px tall and 185px off the left edge

Reported as "the side bar is cut off on the left side". It was not a sidebar —
it was the notification toast, and its geometry measured:

```
x: -175   y: 10   w: 370   h: 814     (viewport 390x844)
```

**Two stylesheets styled `.notification`.** `src/styles/main.css` had a rule for
it — part of the older DOM that stylesheet targets, per the note in
`index.html` — and `showNotification()` in `src/main.js` injected another.

Neither wins as a whole. CSS resolves each *property* independently, so the
injected rule (appended to `<head>` after the link tags) won `top`, `right`,
`left` and `border`, while main.css supplied two declarations nothing overrode:

| From main.css | Effect once combined |
|---|---|
| `bottom: 20px` | with `top: 10px` also set, the box stretches to 814px tall |
| `transform: translateX(-50%)` | shifts it left by half its width: 10 − 185 = **−175px** |

The DOM was perfectly well formed. Only the computed geometry was wrong, which
is why the earlier passes never saw it.

The fix is a **unique class name** — `.fractality-toast` — rather than another
layer of overrides, so no stylesheet written for a different DOM can reach the
element at all. Its own `@keyframes` are prefixed too: keyframe names are global,
and main.css defined its own `slideUp`. The rule now also states every edge
explicitly (`bottom: auto; left: auto; transform: none`) so a future collision
cannot supply one, and the stale `.notification` rules plus the orphaned
`slideUp`/`slideDown` keyframes were deleted from main.css rather than corrected
— a second definition is the bug, and keeping a fixed one invites it back.

Worth noting how this one was introduced: by me, in Part 6.6, adding a mobile
media query to a rule set that was already in a fight it did not know about.

### 8.3 Two new guards, because this is a whole class of bug

**Static.** `npm run health` now compares layout declarations across every
stylesheet *and* every CSS template literal injected from JS, and warns when the
same base selector has the same layout property set from more than one place —
the situation where the outcome depends on load order. Only positioning and
layout properties are compared: sharing a colour is usually deliberate, sharing
an edge or a transform is how elements end up off screen.

It immediately found five more latent collisions (`.hidden`, `.info-row`,
`.result-item`, `.result-header`, `.header-controls` — main.css against
component-injected styles). None currently misrenders, and they are left as
visible warnings rather than churned.

**Runtime.** `npm run browser-check` now raises a toast and asserts it sits
inside the viewport and is not stretched past 40% of the screen height, since
"both opposing edges set" is exactly what that measures.

Both were mutation-checked, and they fail in a usefully different way:

- Re-adding a competing `.fractality-toast` rule to main.css → **the static check
  warns** (`contesting: position, bottom, left, transform`) while the browser
  check stays green, because the explicit edge resets make the collision
  harmless. Correct on both counts: latent risk, no live defect.
- Removing the edge resets *and* re-adding the rule → **the browser check fails
  with `x: -175 … h: 814`**, the owner's exact numbers.

That division is the point. The static check finds the fragile arrangement; the
browser check finds the actual misrender.

### 8.4 One more thing this run caught

The first attempt at the new toast CSS did not build. A comment inside the
injected template read `` Leaving `bottom` unset `` — and a backtick inside a
template literal ends the template literal. Vite failed with
`Expected ';', '}' or <eof>`.

That is Part 1.4's failure mode exactly, reintroduced by hand rather than by
paste, which is a fair reminder that the check exists because the mistake is easy
rather than because chat windows are uniquely bad at it.

## Part 9 — The navigation redesign, and what was hiding behind it

Requested directly: *"none of the spiral buttons seem to do anything except for
print text saying 'switched to' whatever button I pressed... let's find a way to
merge them with the bottom nav bar and then consolidate them all. maybe group

### 9.1 The buttons really did nothing, and the router said so out loud

`AppState._renderView()` had one real branch. For `'bubble'` it showed the 3D

### 9.3 The dock

`src/ui/DockMenu.js`. A row of buttons where each is either a direct action or

```
🌀 View          🔍 Find    🗺 Maps    ☰ More
├ Family                              ├ Export
├ Golden Spiral                       ├ Import
├ Fibonacci Sphere                    ├ Node inspector
├ Fractal Tree                        └ Performance

```

Four buttons, twelve entries, and **every one of them works**. The items are

Two details worth recording:

**Unavailable is not the same as disabled.** A `disabled` button swallows its own

### 9.4 Three latent bugs, each hidden behind the last

The brain-emoji button reported *"Debug panel not available (CACE engine not
loaded)"*. The CACE engine was loaded the whole time.

1. **`fractalityEngine.caceEngine` does not exist.** The engine has always
   constructed `this.cace`. The check read `undefined`, so `NodeDebugPanel` was
   never built and its button always refused.

2. **Fixing that exposed `calculateContextScore()`, which CACEEngine does not
   have.** Two call sites invoked it. `calculateContext()` normalizes across the
   whole visible set, so there is no sensible single-node call to substitute —
   but the engine already stores the score on each node every frame, so
   `FractalityEngine.getContextScore(nodeId)` reads the number the visuals are
   already using. `NodeDebugPanel` now takes a context *provider* rather than the
   CACE engine, which was the only thing it ever asked it for.

3. **Fixing that exposed `fractalityEngine.on('nodeSelected', …)`.** The engine
   has no event emitter and never had one. The call threw the moment it became
   reachable. It now dispatches a `fractality:nodeFocused` window event, matching
   the existing `fractality:expandNode` convention — deliberately not
   `nodeSelected`, which means "please focus this node" and would have looped
   straight back into the handler that calls `setFocus()`.

Each was invisible because the one before it prevented the code from running.
That is what a wall of unreachable code looks like from the outside: one polite
error message.

### 9.5 Fractal Tree only drew half the graph

Found by a unit test, not by looking. `_buildTreeStructure` walks **downward**
through `childIds` from the focus node, so on a standard family view it
positioned 4 of 7 visible nodes — the parent and both siblings were skipped and
kept whatever coordinates the previous layout had given them.

It now roots the tree at the highest visible *ancestor* (guarded against cyclic
`parentId`, since this data comes from user-editable maps) and sweeps any
remaining unreachable node into a ring below. So "Fractal Tree" draws a fractal
tree of everything on screen.

### 9.6 What is deliberately not in the dock

**Social.** The feed controller exists, but its styles live only in

**The Mirror toggle** went with the radial menu, which is the only thing it acted
on. Handedness matters much less for a bottom bar. If it returns it should flip
which side the sheets align to.

### 9.7 The check that would have caught the original problem

`npm run browser-check` gained a section that asserts **effect, not

- nothing is unavailable once the engine has booted
- anything unavailable states a reason

## Part 10 — Node Manager and Cone view, and a correction

Part 9 asserted that "Bubble and Cone were never separate surfaces — they are
layout algorithms". That was wrong about Cone, and it also treated the Node
Manager as covered by the node inspector, which it is not. Both are distinct
features with distinct purposes, described by the owner as:

> The Node Manager is like a file system organizer for the nodes... It's the UI
> for editing the actual relationships of the nodes, allowing you to see more
> than what the display otherwise would, because the idea is for child nodes to
> be hidden inside of parent nodes until that parent is selected and visited.

> Cone view... the top node is a single point at the highest tier (Tier 0), and
> the further down the tiers you go, the more nodes exist in each tier, hence a
> widening of the cone. The idea was that it would be a 2d side view of a cone
> that can be swiped left or right to "spin" the cone, and swiped up or down to
> view higher or lower tiers.

### 10.1 Why the Node Manager is not optional

The 3D view shows very little on purpose: children live inside their parent and
only appear once that parent is visited, so even within one tier you see only the
children of the node you selected. That is the point of the visualisation, and it
makes reorganising impossible — **you cannot move a node to somewhere you cannot
see.**

So the two surfaces divide cleanly: the 3D view reads, the Node Manager edits.

### 10.2 The graph had no edit operations at all

`NodeGraph` had `addNode`, `getNode`, `getChildren`, `getSiblings`,
`getNodesAtDepth` — and nothing else. No remove, no reparent, no reorder. It also
had **two competing sources of truth for children**: `parent.childIds` (an array)
and `childIndex` (a `Set`, derived from each child's `parentId`), which `addNode`
populated while never touching `childIds`.

`childIds` is now the ordered authority and `getChildren` reads it, because a Set
cannot express order and an outline whose "move up" does nothing is not an
outline. `childIndex` and `depthIndex` are derived and maintained by every
mutation.

The new operations: `createNode`, `removeNode`, `setParent`,
`moveWithinSiblings`, `promote`, `demote`, `renameNode`, `getDescendantIds`,
`getRootNodes`, `rebuildIndices`.

Decisions worth recording:

- **`depth` IS the tier**, so reparenting renumbers the whole moved subtree, not
  just the node that moved. Done iteratively — a deep chain is entirely possible
  in a user-built map and this must not depend on stack depth.
- **Cycles are refused.** `setParent` rejects a move into the node's own
  descendant, which would detach that subtree from the graph and hang every
  traversal. `getDescendantIds` is itself cycle-safe, since imported data can
  already describe a loop.
- **Deleting a node with children is two different intentions.** `cascade`
  removes the subtree; `promote` keeps the children and splices them into the
  hole, preserving their order relative to their former uncles. The UI asks
  rather than guessing, because guessing wrong loses work either way.
- **`demote` only uses the preceding sibling.** Falling back to the following one
  would silently reorder the outline as a side effect of an indent.

`tests/graphEditing.test.js` covers this — 24 tests, most of which re-assert the
same two invariants after every operation, because neither is visible from the
UI: every node's depth equals its parent's + 1, and `childIds`, `parentId`,
`childIndex` and `depthIndex` all agree. A bug here does not throw; it produces a
corrupted map that then gets saved to Neo4j.

### 10.3 The Node Manager

`src/ui/NodeManagerPanel.js`. A full outline of the graph — every node, not just
the visible ones — with tier numbers, child counts, expand/collapse, and eight
actions: add child, add sibling, rename, move out a tier, move in a tier, reorder
up, reorder down, delete.

Selecting a row also focuses that node in the 3D view, so the two surfaces stay
pointed at the same thing; the row the 3D view is looking at is marked separately
from the row you have selected.

Actions that cannot apply say why — "Already at tier 0", "Nothing above it to
move into" — following the same rule as the dock. Every edit calls
`engine.notifyGraphChanged()`, which is new and necessary: `loadData()` was the
only thing that re-analysed the graph, and it also resets focus, so using it
after an edit would throw the user back to the root each time they added a node.
Three caches would otherwise serve stale answers — the family view's 1-second
selection cache, the CACE analysis, and the layout.

### 10.4 The Cone view

`src/ui/ConeView.js`. A 2D side elevation on a canvas, driven by two gestures:
drag sideways to spin, drag up and down to travel the tiers. Pointer events, so
one code path covers touch, mouse and pen.

Nodes are laid out as a **cone tree**: each subtree owns a wedge of the circle,
divided among its children in proportion to how many leaves each contains.
Weighting by leaf count rather than splitting evenly stops a branch with one
child claiming as much of the circle as a branch with thirty, which is what makes
the widening legible rather than decorative.

The projection is a genuine side view — horizontal position is `sin` of the
angle, and `cos` only decides how near the viewer a node is, feeding size,
opacity and paint order. Tier rings are drawn as the ellipse a circle makes seen
nearly edge-on.

Only the front third of the current tier is labelled; wider than that and the
labels overlap, which is worse than not labelling them. The 3D engine is paused
while the cone covers the screen — otherwise it renders frames nobody can see,
which on a phone is battery spent on nothing.

### 10.5 The default map's tiers were wrong, and had always been

Found by the new browser check, not by looking: **15 of the 36 nodes in the
default generated map had a depth equal to their parent's.**

`TestDataGenerator.generateGoldenSpiral()` reassigned its `parent` variable to
the first child *inside* the loop that was still creating that level's children.
So the second and later children of a level were attached to their own sibling
while still being given the level's depth:

```js
for (let i = 0; i < childCount; i++) {
    const child = new NodeData(id, level + 1, {...});
    child.parentId = parent.id;      // `parent` already moved on
    if (i === 0) parent = child;     // ...here, mid-loop
}
```

Since depth is the tier, that made the tier numbers, the cone view's rings and
the family layout wrong together. Nothing noticed because nothing checked — the
3D view draws whatever positions it is given.

Fixed two ways, deliberately: the generator now pins the level's parent before
the inner loop and derives depth from `levelParent.depth + 1` so the two cannot
disagree again; and `loadData()` calls `rebuildIndices()` on every graph it
receives, whatever produced it. Graphs arrive from three places — the generator,
an imported file, the API — and any of them can carry a depth that disagrees with
its parent links. Normalising once at the boundary means every consumer
downstream can take `depth` literally.

### 10.6 A test that passed while asserting nothing

The first version of the generator regression test called
`generator.generate('spiral', …)`. There is no `generate()` method — the real
ones are `generateGoldenSpiral()`, `generateBalancedTree()`, `generateOrganic()`
and `generateTestPattern()`. It was wrapped in `try { … } catch { continue }`, so
all three patterns threw, all three were skipped, and the test reported success.

Caught only by mutation-testing it: reverting the generator fix left the suite
green. Rewritten to name each method explicitly with no swallowing catch, it now
fails with `goldenSpiral produced 15 node(s) whose depth disagrees with its
parent` — the original defect, exactly.

The lesson is narrower than "write better tests": a `catch` that continues turns
a test into a no-op, and a green suite is not evidence unless something has been
seen to make it red.

### 10.7 Coverage

`npm run browser-check` gained two sections, now 82 checks total.

**Node Manager** — that the outline lists *all* nodes rather than only the ones
the 3D view shows, that each of the seven edit actions has the right effect on
the node count, and, after every single edit, that the graph is still
structurally consistent. That last assertion is what found §10.5.

**Cone view** — that it opens unclipped, that every node is hit-testable, that a
sideways drag spins without changing tier, that a vertical drag changes tier and
settles on a whole number, that tier travel clamps at both ends, that the readout
matches the tier, that tapping a node selects it, and that the 3D engine is
paused while covered and resumed on close.

## Part 11 — The feed

Outstanding item 2 — *"`ResonanceEngine` has no network behind it... the social
half of 'social mind mapping' does not exist yet"* — is now built. Text and links
only; images are still blocked on object storage.

### 11.1 What the design brief actually asked for

> I also like the idea of having a "newsfeed" where people can scroll through
> things that their friends or maybe other random people post as text content,
> links, photos and whatnot. I don't want it to be the main thing, but rather a
> feature to help replace the scrolling of modern corporate social media.

"Replace the scrolling" is a design constraint, not a throwaway. Two things follow
from it directly, and both are choices rather than gaps:

- **No infinite scroll.** A "Load more" button, so continuing is a decision.
- **No ranking.** Strictly reverse-chronological, so the order is explicable.

A feed you can reach the end of is the point.

### 11.2 A separate component, not a retrofit

`ResonanceFeedController` already existed, and reusing it was the obvious move
until the cost showed up: it is styled entirely by `mobile-menu.css`, which
`index.html` does not load, and which targets MenuController's DOM (`#menu-root`,
`#menu-container`). Loading it would collide with the shell.

So `src/ui/FeedPanel.js` is new, with self-contained styles, and
`ResonanceFeedController` stays with the mobile app it was written for.

Its classes are prefixed `pulsefeed-`, not `feed-`, and that was not a guess:
`npm run health` flagged `.feed-title` as styled from two places the moment the
first version was written. The check added in Part 8 earned its keep on the very
next component.

### 11.3 Backend

```
(:User)-[:POSTED]->(:Pulse)
(:User)-[:RESONATED_WITH]->(:Pulse)
(:User)-[:REPORTED {reason, at}]->(:Pulse)
(:User)-[:BLOCKED]->(:User)
```

`resonators` is a count of relationships and `resonance` is derived from it. A
stored counter could drift from the relationships it summarises, and a like count
that disagrees with who liked it is worse than a slower query.

`MERGE` for resonance, reports and blocks, so all three are idempotent — a double
tap cannot make two relationships, and one person cannot inflate a report count by
pressing repeatedly.

The block filter lives **inside** the feed query. Filtering in Python afterwards
would make `limit` mean "up to N, minus however many were blocked", so blocking a
prolific poster would quietly produce short pages.

### 11.4 Moderation was built with it, not after it

`api/README.md` has said since Part 5 that a public feed needs report/block flows,
admin delete and rate limiting *before* it accepts content from strangers — and
that this carries legal obligations, not just product ones. Shipping the feed
without them would have made that note a lie.

| Control | How |
|---|---|
| Delete your own post | ownership is in the Cypher `MATCH`, so there is no check-then-act window and no way to reach another author's pulse |
| Report | fixed reason list, one report per reporter |
| Block | hides an author from *your* feed only; self-blocking refused, since it would silently empty your own |
| Rate limit | 20 posts/hour, counted from stored pulses |

The rate limit deliberately does not use an in-process counter: Render runs more
than one instance, so a per-process counter would hand each of them a separate
allowance.

Report reasons are a fixed list rather than free text. The reason is a routing
signal for a human, and an open text field on a report endpoint is itself an abuse
channel.

Two things are still missing and are recorded as such: an **admin review queue**
(there is no admin role in this project yet — reports go to the service log at
warning level) and **image scanning**, which cannot exist before image uploads do.

### 11.5 Hostile content is in the fixture, not a separate test

The feed renders text written by strangers, which makes it the one component where
a convenient template literal is a stored-XSS vector. So the browser check's feed
fixture includes a post whose title is `<img src=x onerror=...>`, whose body is a
`<script>`, whose author name is `<b>Evil</b>`, and whose link is a `javascript:`
URL.

That fixture found a real bug immediately. `safeUrl()` returns **`null`** for a URL
it will not vouch for; the first version of the panel compared against `'#'`:

```js
const href = safeUrl(pulse.media.url);
if (href !== '#') { link.href = href; }     // null !== '#', so this ran
```

`link.href = null` renders as the literal string `"null"`, which is inert — so the
`javascript:` URL did not execute, by luck rather than by design. A different
sentinel, or a browser that resolved `null` differently, and it would have been a
working injection.

A second, subtler point came out of the fix: the link's `href` is assigned the
**original** URL, not `safeUrl`'s return value. `safeUrl` HTML-escapes what it
vouches for, which is correct for `innerHTML` and wrong for a property — a query
string containing `&` would become `&amp;`, i.e. a different URL. The scheme has
already been checked by then, so the raw value is the safe one to assign. There is
a check asserting `?a=1&b=2` survives intact.

Mutation-checked: changing one `textContent` to `innerHTML` makes the hostile post
execute (`window.__pwned = 1`) and the check reports it.

### 11.6 What is NOT verified

**The feed's Cypher had never run against a database when this was written.** It has
since: all 47 integration tests pass against a live AuraDB Free instance (88s). The
paragraph is kept rather than deleted because the reason still applies to anything
written here — this environment has no Neo4j, no Docker daemon, and no route to
download one (`dist.neo4j.org` is blocked by the proxy, as is `fractiverse.com`), so
Cypher written here is unverified until someone runs it somewhere else.

The 35 router tests do run, and cover authorization, rate limiting and validation
with the repository stubbed. That is a different guarantee, and it is not a
substitute.

So: **run `pytest api/tests/test_integration_neo4j.py -v` before trusting the feed
with anything.** This is exactly the position the mind-map Cypher was in at the
end of Part 5, and it stayed there until it was run against live AuraDB — at which
point it passed, but only because a fixture-scope bug had already been fixed by
reading it very carefully.

### 11.7 Two bugs of my own, found by running things

- **A whitespace-only title was accepted.** `Field(min_length=1)` runs *before* a
  plain `field_validator`, so `"   "` satisfied the constraint as three characters
  and was then stripped to empty. Fixed with `mode="before"`, so trimming happens
  first and the constraint sees what will actually be stored.
- **The `safeUrl` sentinel**, above.

Both were found by executing the code rather than reading it — the first by a test
asserting an empty title is refused, the second by putting a `javascript:` URL in
a fixture.

## Part 12 — Turtle export, and the export that had never worked

Asked as a design question — *"instead of mind maps saving and exporting/importing
as json files, would it make sense to have it be .ttl files instead? we're kind of
creating ontological maps here"* — and it is a good instinct. These maps are
concept hierarchies with labels, types and tags, which is what RDF is for.

### 12.1 Interchange format, not internal format

The answer that mattered was separating the two. Turtle is now an **export and
import format alongside JSON**; JSON stays the wire format between browser and
API, and Neo4j stays the store. Two specific reasons, not general caution:

**RDF has no inherent ordering.** `:a skos:narrower :b, :c` is a *set*. Sibling
order became authoritative in Part 10 when the Node Manager gained the ability to
reorder, so a naive translation would have silently dropped it. Order is carried
explicitly in `fract:position`, and three separate tests assert it survives —
including one whose labels are deliberately reverse-alphabetical, so the assertion
cannot pass on sorting luck.

**Transient visual state is not ontology.** Positions and colours are recomputed
by the layout engine every frame, so they are not exported. A re-imported map is
laid out afresh. That makes the Turtle export deliberately narrower than the JSON
one, which is the right trade for an interchange format.

### 12.2 SKOS, not OWL

`skos:broader`/`skos:narrower` are *deliberately* vague about whether a child is a
subclass, a part, or simply a narrower idea — which is exactly what a mind map
means. OWL's `subClassOf` would force that decision on every single edge, and it
would be the wrong one about half the time.

```turtle
@prefix skos: <http://www.w3.org/2004/02/skos/core#>.
@prefix dcterms: <http://purl.org/dc/terms/>.
@prefix fract: <https://fractiverse.com/ns#>.
@prefix : <https://fractiverse.com/map/demo#>.

<https://fractiverse.com/map/demo> a skos:ConceptScheme;
    dcterms:title "My Ontology";
    skos:hasTopConcept :root.
:consciousness a skos:Concept;
    skos:prefLabel "Consciousness";
    dcterms:description "What recursion feels like from the inside";
    fract:tier 1;
    fract:tag "mind", "recursion";
    skos:broader :root;
    fract:position 0.
```

App-specific terms live in their own `fract:` namespace rather than squatting on
SKOS's. Unrecognised `fract:*` predicates are read back into metadata on import,
so a field a future version adds survives a round trip through this one.

`skos:narrower` is emitted as well as `skos:broader`, for readers that follow only
one direction — but on import **`broader` is authoritative** and `narrower` only
fills gaps. Treating them as equal would let a file contradict itself.

### 12.3 The library is lazy, and that is verified

N3 handles the parsing, because writing Turtle is easy and parsing it correctly is
not — prefixes, blank nodes, collections, escapes. It is loaded with a dynamic
`import()` so it is not in the initial bundle, and the browser check asserts the
`turtle` chunk is **not** requested on page load and **is** requested after
pressing Export.

### 12.4 The JSON export had never worked

Found while wiring the new buttons next to the old ones. `exportToCLI()`
serialised `nodeBridge.exportForCLI()`, which reads the CLI bridge's *own* node
collection — and that is only populated by the local Python helper. Measured on
the deployed build:

```
engine graph:  36 nodes
bridge export:  0 nodes
```

So **Export produced a valid JSON file containing zero nodes**, on every
deployment, for the entire life of the feature. Silently: a download that appears
to succeed, a file that opens fine, and nothing in it.

Both export paths now serialise `fractalityEngine.nodeGraph` — the graph actually
on screen. Import is one button that detects JSON or Turtle from the file's
contents rather than asking, since the user already has a file and asking only
invites the wrong answer. `FractalNode.toJSON()` happens to be shape-compatible
with `NodeGraph.fromJSON`, so an old CLI export still imports.

The browser check asserts the file's **contents** rather than that a download
happened — which is the distinction the original bug lived in. Mutation-checked:
restoring the bridge-based export reports `the JSON export contains ZERO nodes —
the original bug`.

### 12.5 Two bugs in the converter, both found by tests

- **Base IRI inference was poisoned by the ConceptScheme.** The scheme's IRI is
  the base minus its trailing `#`, so the longest-common-prefix calculation
  collapsed to `.../map/` and every id came out as `test#alpha` instead of
  `alpha`. Fixed by inferring the base from the concepts alone.
- **Untyped numeric literals came back as strings.** `0.5` was written without a
  datatype, making it `xsd:string`, so a round trip returned `"0.5"`. Integers had
  a datatype and were fine, which is why only one test caught it. Floats now get
  `xsd:double` and booleans `xsd:boolean`.

`tests/turtle.test.js` is 17 tests, and the ones that earned their place are the
awkward ones: ids containing spaces, slashes, `#` and non-ASCII; labels containing
quotes, newlines and backslashes; a foreign SKOS file using neither our base IRI
nor our terms; a file stating only `narrower`; a legal Turtle **cycle**, which is
detached with a warning rather than handed to a layout engine that assumes a tree.

### 12.6 render.yaml reconciled

It described only the static site; the API block was commented out, because the
API service was created by hand in the dashboard. Both services are now described.

The header now says the thing that was missing: **a Blueprint only governs services
Render created from a Blueprint.** Both live services were made by hand, so this
file is documentation — accurate documentation, but Render is not reading it, and
editing it changes nothing about the running deployment. It exists so a service
that is lost can be rebuilt without reconstructing its settings from memory.

Anything secret, or that only the dashboard knows, is `sync: false`. Hardcoding a
guessed API hostname would be worse than leaving it unset, because a Blueprint
sync would then overwrite a working value with a wrong one.

`plan: free` is recorded as what is actually running, with the trade-off written
down rather than asserted: a free instance spins down after ~15 minutes idle and
the next request waits ~50 seconds, and that hurts *more* at low traffic, not less
— a few people checking in daily means almost every visit is a cold start. The
note names the two conditions that should trigger an upgrade (chat existing, or
showing it to someone whose first impression matters) instead of the previous
blanket "not the free tier".

## Part 13 — Identity, and two bugs that were not what they looked like

A desktop testing session produced a list. Three items on it had causes other than
the obvious one, which is the interesting part.

### 13.1 "Maps saved on my phone don't show up on desktop"

Not a sync failure. The maps were in Neo4j the whole time.

Signing in had **no home of its own**. The only two ways to do it were a button
inside the Maps panel's header and one inside the feed composer. So a fresh desktop
browser was never signed in — and `MapsPanel.refresh()` branches on exactly that:

```js
const maps = signedIn ? await listMyMaps() : await listPublicMaps();
```

An anonymous visitor gets the public list. The maps in question were private, so
they were correctly absent. Reported as a sync problem because there is no way to
tell those two apart from the outside.

Fixed by giving identity a dock entry of its own — the first row of ☰ More, which
reads "Sign in" or "Account" depending on the session. `DockMenu` gained support
for callable labels to make that possible, re-resolved on every `refresh()` so the
label tracks the session without a rebuild (a rebuild closes any open sheet).

### 13.2 "The dock disappears when Cone View is selected"

Overlay stacking. The Cone view is `z-index: 900` across the whole viewport; the
dock was `z-index: 30`.

The cone's height was written as `bottom: var(--dock-height)`, which clears a
**bottom**-anchored dock. On a desktop the dock is at the **top**, where
`--dock-height` is 0 — so the cone covered it completely, and the only way back
was a page refresh.

Two changes, because either alone would have been fragile:

- The dock is now `z-index: 1200`. Navigation should outrank the things it
  navigates to, as a rule and not as a special case for this overlay.
- `--dock-top-height` joins `--dock-height`, and exactly one of the two is non-zero.
  Full-screen overlays inset from both, so they clear the dock at whichever edge it
  happens to be on.

### 13.3 "Cone view doesn't recognise name changes made in Node Manager"

The most instructive one, because **the cone was never showing stale data**.

Instrumenting `fillText` proved renamed labels were painted and old ones were not.
My first reading of that instrumentation was wrong in a way worth recording: it
counted a `Set` of painted *strings* and found 21 for 36 nodes, which I took for
"15 nodes are never labelled". The test data simply reuses labels — 36 nodes carry
21 distinct names. Measured by node id instead, every node was reachable.

The real cause is that a label was only drawn for a node on the **focused tier**
whose `nearness > 0.45` — the front third of one ring. Renaming a node and coming
to the cone to look at it therefore showed nothing, unless that node happened to be
on the focused tier and facing the viewer. Indistinguishable from the cone ignoring
the edit; the new name simply had nowhere to appear.

Two fixes:

- **The readout always names the selected node.** Select it anywhere — the Node
  Manager, the 3D view, a tap in the cone — and its current name is on screen.
  This is the one that closes the reported loop.
- **Labels are placed with collision testing** rather than an arc cutoff, so the
  whole focused tier is labelled and only genuinely overlapping text is dropped.
  The selected node is placed first, so it never loses a collision.

The general lesson: "it is not picking up my change" and "my change has nowhere to
be seen" are the same report, and only one of them is a data bug.

### 13.4 Feed posts were attributed to "Anonymous"

Clerk's session JWT carries no name. A default token has `sub`, `iss` and `exp`
and nothing else unless a custom JWT template is configured, so:

```python
username = claims.get("username") or claims.get("name")   # both absent -> None
```

The display name has to live somewhere this API can read, which means the User
node. `GET /me` and `PATCH /me` were added, and the pulse queries now prefer
`display_name` over the provider's `username`.

The frontend seeds it once from Clerk's client (which *does* know the name), and
**only when no name has been set** — so a name the user chose is never overwritten
by the provider's on a later sign-in.

`PATCH /me` distinguishes an omitted field from an explicit null. That is not
pedantry: collapse them and an avatar can be set but never removed. Two tests
assert the distinction directly.

### 13.5 Map visibility had no control at all

Every map was created private and there was no way to publish one, which made
"sharing" mean share links exclusively.

A cycling button — 🔒 Private → 🔗 Link only → 🌍 Public — because the three states
have a natural order and it is one tap either way. `unlisted` sits in the middle
deliberately: it is not a lesser `public` but "not listed, readable with a link",
which is the state a share link is for.

Publishing asks for confirmation and un-publishing does not. Making something
visible to strangers is the step that cannot be taken back for anyone who has
already looked.

### 13.6 Editing your own posts

`PATCH /pulses/{id}`, with ownership in the Cypher `MATCH` so it cannot reach
another author's post and there is no window between checking and writing.

Every edit stamps `edited_at`, and the card shows an "edited" badge. A feed where
posts can be silently rewritten after people have responded to them is worse than
one without editing at all.

The edit model reuses `PulseCreate`'s validators by construction rather than by
copying them, so a link refused on the way in cannot become acceptable on an edit.
There is a test for exactly that.

### 13.7 Coverage

`api/tests/test_profile_and_edits.py` — 16 tests, weighted toward the two things
that fail silently: PATCH semantics (omitted vs null) and edit authorization.

`npm run browser-check` gained an "identity and overlays" section: that the dock
exposes an identity entry, that the account panel opens and states what is
available, that the dock stays reachable with the Cone view open, that the cone
does not overlap it, that the readout names the selected node, and that visibility
cycles and can reach public.

## Part 14 — One graph, two surfaces

### 14.1 "The renamed node appeared in Cone View but not in the Node Manager"

Reported after a real round trip: rename a node on a phone, save, open the map on
a desktop. The cone showed the new name. The outline showed the old one.

Nothing was stale about the data. `FractalityEngine.loadData()` does not mutate
the existing graph — it **replaces** `this.nodeGraph` with a different object, and
nothing told anyone. Which surface noticed depended entirely on how each one reads:

- `ConeView` redraws from `getGraph()` on every frame, so it re-reads the
  reference each time and could never be wrong.
- `NodeManagerPanel` renders once and keeps the DOM, so it kept displaying an
  outline built from a graph the engine had already discarded.

The bug was not in either surface. It was the missing announcement between them.
Any future surface that caches a render would have inherited the same fault, so
the fix belongs in the engine:

```js
this._announce('fractality:graphReplaced');   // end of loadData()
```

with `notifyGraphChanged()` announcing `fractality:graphChanged` the same way.

The Node Manager listens for both. Re-rendering is the easy half; the subtle half
is the state it holds that belonged to the *old* graph:

```js
if (this.selectedId && !graph?.getNode(this.selectedId)) {
    this.selectedId = null;
}
// Collapse state is keyed by node id, and those ids belong to the old
// graph. Keeping it would hide branches of the new one at random.
this.collapsed.clear();
```

A collapse set carried across a graph swap is worse than a stale render, because
it fails intermittently: it only hides something when an id happens to collide.

`loadData()` also now calls `nodeGraph.rebuildIndices()`, so depths are normalised
whatever the graph arrived from — API, JSON file, or Turtle.

### 14.2 Your most recent map opens by default

Signing in and then being shown the generated demo map is the wrong default: the
map you were last working on is what you came back for. On boot, when there is an
API and you are signed in, `openMostRecentMap()` asks for one map
(`listMyMaps({ limit: 1 })`, ordered `updated_at DESC` by the server) and opens it.

Every failure path falls through silently to the demo — no API, not signed in, no
maps yet, a request that fails. A boot sequence must not be able to hang on a
network call, so this one is allowed to give up without explaining itself.

### 14.3 Coverage

Two checks in the "identity and overlays" section reproduce the exact reported
scenario: rename a node with the Node Manager open, load a replacement graph, and
assert the outline follows it — and that the outline lists every node of the new
graph, not a truncated tree.

The visibility check was tightened in the same pass. It printed the resulting
label in its pass message, and that label was `undefined`: `refresh()` re-renders
through the session path, which drops the owner controls in a build with no Clerk
key, so the button it looked for was gone. The assertion underneath was real, but
the message read like a bug. It now re-renders as owner and asserts the label
actually followed the change — verified by mutation: pinning the label to
"Private" makes the check fail.

## Part 15 — Node pages

The map's point is not the shape of the tree. Every node stands for a concept, and
the value is the writing attached to those concepts — "each node a link to a
markdown page, kind of like how Obsidian works, only with hierarchy and more
complex relationships". Tier, branch and level are metadata about where a concept
sits, not what it is.

So a node now has a page, and the Node Manager is where you write it.

### 15.1 One field, four layers

`metadata.content`, carried the whole way down:

| Layer | How |
|---|---|
| `NodeData` | `metadata.content`, with `NodeGraph.setContent()` and a `content` getter |
| API model | `NodeMetadata.content`, capped at 64 KB per node |
| Neo4j | a real `content` property, not a key inside `metadata_json` |
| Turtle | `schema:text` |

Three of those choices are worth stating.

**An empty page deletes the key rather than storing `''`.** Most nodes of a large
map will never have a page. A stored empty string would be written to every export,
every Turtle file and every database row for nothing. The `content` getter returns
`''` either way, so no caller has to care.

**`content` is a Neo4j property, not part of `metadata_json`.** It is the one field
a reader may want without the rest of the node, and the one large enough to be
worth projecting away. Burying 64 KB in a JSON blob makes that impossible.

That change had a trap in it. `content` used to be free-form metadata, tolerated by
`NodeMetadata`'s `extra: "allow"` and swept into `metadata_json` — so maps saved
before the change carry it there. Reading such a row with both sources populated is

```python
NodeMetadata(content=..., **{"content": ...})
```

which is a `TypeError`, not a silent preference: every map saved under the old
shape would have failed to open with a 500. `_row_to_node` pops the key out of the
blob and prefers the column when it has something. Four tests cover it, and
reverting the `pop` to a `get` fails all four.

**`schema:text`, not `dcterms:description`.** `dcterms:description` is already the
one-line summary shown in lists; handing a reader a whole document under that
predicate would be wrong. `schema:text` means the textual content of a work, which
is exactly this. Files written before that decision used `fract:content`, and the
importer still accepts it — filling only a gap, because quad order is not
guaranteed and a file carrying both must not depend on which N3 hands over last.

### 15.2 A markdown renderer, written rather than installed

`src/ui/markdown.js` renders markdown to DOM. Two reasons it is not a dependency.

**Safety.** Every markdown library returns an HTML *string*, which has to be
assigned to `innerHTML`, which makes the sanitiser the only thing between a shared
map and stored XSS in every reader's browser. This renderer calls `createElement`
and puts text in through `textContent`, so there is no HTML string at any point and
nothing to sanitise. A page containing `<script>` produces a text node reading
`<script>`, because that is the only thing a text node can produce. The single
place a value reaches an attribute is a link's `href`, and that goes through
`safeUrl`.

**Size.** A full CommonMark implementation is tens of kilobytes of spec this does
not need.

Deliberately absent: raw HTML passthrough. In a format whose whole point here is
that it cannot inject markup, an escape hatch back to markup would defeat it.

Three smaller decisions:

- **Images render as links, not `<img>`.** A remote image in a shared page is a
  request to a third party from every reader's browser, leaking their IP address
  and letting whoever hosts it count them. The reference is kept; the fetch is the
  reader's choice.
- **Task-list checkboxes are disabled.** Ticking one would change the view without
  changing the markdown behind it, which reads as a save that silently did not
  happen.
- **An unterminated fence runs to the end of the document.** Half-written notes are
  the normal case, and losing everything after a stray ``` while typing would look
  like the editor ate the page.

`__` and `**` are separate rules, because they are not equivalent: markdown treats
an underscore inside a word as literal so that `snake_case_name` is a name. One
combined pattern gets this wrong in one direction or the other — the first version
here rendered `snake_case_name` with emphasis in the middle, and a test caught it.

62 tests in `tests/markdown.test.js`, most of them hostile input, including two
sweeps that assert no input can produce an element or an `on*` attribute the
renderer does not document. jsdom rather than a hand-rolled shim, because a shim
lets a bug pass by implementing whatever the code happens to call; the
security assertions are repeated against a real browser in `browser-check`.

### 15.3 The panel is now full width, and half of it is the page

The outline was a 380px box in the corner. It is now the width of the screen
between the two docks, split into the outline and the page, with the page taking
the larger half. Viewing the 3D map while reorganising was never useful — you
cannot move a node to somewhere the 3D view will not show you — and a page needs
room to be read.

On a phone the two halves take turns behind a tab switch. 340px of outline plus a
page is not readable on a phone, and a page squeezed into half a phone is not a
page.

**There is no Save button.** The editor commits on a 600 ms debounce, on blur, when
the selection changes, and when the panel closes. A page you typed and then clicked
away from is a page you wrote; a dialog asking whether you meant it is a trap you
have to answer before you are allowed to look at anything else.

That design has one sharp edge, and it is the bug worth naming. A debounce still
pending when the selection changes would write one node's page onto another. The
commit is therefore keyed on the id the *text was loaded for*, not on the current
selection:

```js
const id = this._editingId;
```

Changing that one word to `this.selectedId` makes a browser check fail. It is the
kind of bug that is not noticed until much later, once the wrong page is the only
page.

A content edit deliberately does **not** call `onGraphChanged()`. That invalidates
the family view, the CACE analysis and the layout, none of which depend on a node's
text — so on every debounce tick it would be pure waste. It would also announce a
graph change, which re-enters `render()`, which commits again: a loop that only
terminates by accident.

The outline marks which nodes have a page with a `◈`, whose tooltip is the first
line with the markdown stripped out. Without it there is no way to tell a concept
that has been thought through from one that is still just a word, and finding out
means clicking every row.

### 15.4 [[Wiki links]]

`[[Duality]]` in a page links to the node named Duality — resolved by label first,
because that is what a person types, case-insensitively, falling back to the id.
Clicking one moves the selection, the 3D focus and therefore the cone.

A link to a node that does not exist is still shown, marked with a dashed border
and inert. Referring to something you have not made yet is a normal thing to write;
hiding the reference would lose the intent and making it clickable would go
nowhere.

The link is a `<button>`, not an `<a>`. It navigates this app's own state and has no
URL to point at — which also means it cannot carry one.

### 15.5 One selection, three surfaces

"The relationship between the two is where I will spend most of my time and they
should talk to each other."

They already shared a channel and neither listened to it. All three surfaces route
selection through the engine's focus, and `fractality:focusChanged` had been firing
since long before any of this — nothing was subscribed. So:

- The **Node Manager** follows `focusChanged`: it moves its selection, expands
  whatever branch was hiding the node, and scrolls the row into view. A selection
  nobody can see reads as nothing having happened.
- `show()` now takes the engine's focus over its own remembered `selectedId`. The
  engine's focus is the shared selection and the panel's field is a cache of it;
  the other way round meant selecting a node in the cone with the panel closed,
  reopening it, and finding it still pointed at whatever was selected there last.
- The **Cone** turns and scrolls to the focused node rather than only highlighting
  it. Highlighting was not enough: the cone shows one tier's neighbourhood at a
  time, so selecting a tier-4 node while looking at tier 0 drew a highlight nobody
  could see. Spinning matters as much as scrolling — a node on the far side is
  drawn small, dim and behind everything, and reads as absent.
- The cone does **not** re-aim on its own taps. Snapping the node the user just
  pointed at from wherever they saw it to the front moves the thing they were
  looking at as a reward for looking at it.

### 15.6 Coverage

A "node pages" section in `browser-check`, 19 checks: writing a page and having it
reach the graph, markdown rendering, wiki-link resolution and navigation, the
outline's page marker, the pending-edit race, hostile content in a real browser,
and both directions of selection between the outline and the cone.

Four of those were mutation-tested — reverting the `_editingId` guard, the cone's
focus listener, the self-initiated-tap flag, and the outline's listener each make a
check fail.

The fifth mutation is the one worth recording, because it exposed a **check that
was proving the wrong thing**. Deleting the cone's focus listener entirely left
"selecting in the outline turns the cone to that node" passing, because that check
reaches the cone through `show()` — which aims on the way in regardless of what the
listener does. The live case needed its own check: cone already open, focus changed
elsewhere, cone moves. A check that passes with the feature removed is not
coverage, and only a mutation run will tell you which of yours are like that.

## Part 16 — Resonance, and why it shows you no numbers

The feed had a "resonate" button that counted presses and drew a saturating curve
over the count. That is a like count with a nicer name, and it has the same effect:
it makes writing into competing.

What replaced it answers two different questions, and keeps them apart.

### 16.1 Which engine is this? Neither of them

Worth stating plainly, because the project has two things with promising names and
neither does this.

**`CACEEngine`** — Context And Complexity Engine — operates on *mind map nodes*. It
scores a node by descendant count, depth, connection count, sibling rank, recent
access and an energy factor. It has nothing to do with the feed and never did.

**`ResonanceEngine`** is not a scoring engine at all despite the name. It is a
transport client for the feed, currently backed by `localStorage`, and its
`resonate(pulseId)` sets a boolean. It is reachable only from `src/mobile/MobileApp.js`,
which is not an entry point any more — `index.html` loads `src/main.js` alone.

So the resonance model is a new module, `api/resonance.py`. That is a deliberate
choice not to add a fifth grand engine to a project whose original problem was
half-built engines: it is about 200 lines, it is arithmetic anyone can follow, and
it is not collaborative filtering or a neural anything. With a handful of friends
and family there is not enough data for anything cleverer to be *honest*, and a
model whose output nobody can account for is a bad thing to put between people and
what they read.

### 16.2 A five-notch slider, not a button

`-2 -1 0 +1 +2`, zero in the middle and the default. "Dissonant" on the left,
"Resonant" on the right; the notches show bare digits, because a minus sign in a
26px target reads as a hyphen and the side already carries the sign.

Three decisions inside that:

**The scale is -2..+2, not 1..5.** A reader who never touches the slider has said
nothing, rather than having given one star. On a 1..5 scale "no opinion" has to be
either absent or a low score, and both are wrong.

**It is symmetric.** An asymmetric scale quietly tells people which answer is
expected.

**The negative side is about fit, not merit.** "This is dissonant for me" is a
statement about the listener. "Dislike" is a verdict on the author. Same data,
without the invitation to be cruel.

Pressing the notch you are already on clears the rating. It is the only way back to
"no opinion" once one has been given, and an action that rare does not deserve its
own control.

### 16.3 Nobody sees a tally. Not even the author

This is the part that makes the rest work, and it is enforced as an absence:

- `resonators` and the derived `resonance` score are **gone from the wire**. The
  only resonance figure on a `Pulse` is `my_rating` — the caller's own.
- The author of a post cannot see how anyone rated it. There is no endpoint, no
  field, and an integration test asserts it against a real database rather than only
  against the serialiser.
- Impressions are recorded, and are never read back to any user.

A test asserts the wire format field-by-field rather than checking the UI, because
a field that exists will eventually get rendered by someone.

The design brief was explicit about why: *"seeing numbers is part of what people get
addicted to; myself included."* The numbers can be turned on later. They cannot be
turned off later, because by then people will have started competing over them.

### 16.4 The only number shown is about you

Each pulse carries `predicted` (-1..+1) and `prediction_confidence` (0..1),
computed from **that reader's own past ratings and nobody else's**. The feed draws
it as a small arc: cyan for resonance, red for dissonance, arc length for magnitude,
opacity for confidence.

Two readers looking at the same post should see different gauges. If they ever see
the same one, the model has become a popularity measure wearing a personal label —
so `test_two_readers_of_the_same_post_get_different_answers` exists.

The model is an affinity per tag and per author, shrunk toward neutral:

```
affinity = sum(ratings) / (count + 3)
```

The `+ 3` is the whole difference between this and a mean. Without it, a single +2
rating on a tag produces a maximally confident affinity, and the gauge swings to its
extreme on a reader's first tap — which reads as the app having decided something
about you on no evidence. Ten +2 ratings yield 0.77, not 1.0.

Four more decisions that each have a test:

- **Below 8 ratings there is no prediction at all.** The arithmetic still produces a
  number and that number is noise. A confident-looking gauge invites belief.
- **A post with nothing in common with your history gets `None`, not neutral.**
  Saying "neutral" would be a claim; `None` is the truth. The UI draws nothing,
  because unknown must not look like zero.
- **The tag component is a mean, not a sum.** Otherwise adding tags raises your
  score, which is a lever, which means someone will pull it.
- **Weights are renormalised over the components that exist.** Without that, a post
  by someone new always reads as half as resonant as the same post by a known
  author — which says something about the author and nothing about the post.

A rating of `0` is not evidence of a neutral opinion; it is the absence of one, and
is not counted. Counting it would drag every affinity toward neutral in proportion
to how much of the feed you scrolled past, so the more you read, the less the model
would think anything resonated with you.

### 16.5 Impressions, which are the denominator and not a reading log

Without knowing how many people had the chance to rate a post, a post that landed
badly and a post nobody was shown are the same thing: both have no ratings.

`(:User)-[:SAW]->(:Pulse)`, MERGE'd, so one reader counts once however many times a
post scrolls past. What is deliberately *not* recorded: how long you looked, how
often, or in what order. And nothing reads it back to any user.

On the client, a post counts as seen when its card has actually been **half on
screen**, via `IntersectionObserver` — not when the API returned it. Counting
everything returned would inflate the denominator with posts nobody scrolled to,
making every post look like it landed worse than it did. Your own posts are skipped
at both ends: seeing your own writing says nothing about what resonates with you,
and counting it would let a prolific poster's own feed dominate their model.

Where there is no `IntersectionObserver`, nothing is recorded at all rather than
falling back to "the server sent it". A missing measurement beats a wrong one.

### 16.6 The feed is still strictly chronological

The predictions are shown to the reader; they do **not** order the feed. An order
chosen by a model is a feed that decides what you see, which is the thing this is
meant to be an alternative to. The gauge is a hint you can ignore, in a feed whose
order you can predict.

### 16.7 Coverage, and a check that was testing the browser

23 unit tests on the model, 49 on the feed's endpoints, 14 new integration tests
against a real database, and 12 new browser checks in a feed section now at 27.

Five mutations confirmed the client guards bite: counting your own posts as
impressions, drawing a gauge with no prediction, a notch that cannot clear itself,
and a batch that sends repeats each make a check fail.

The sixth is worth recording. Deleting the client's `unobserve()` call broke
nothing, because `IntersectionObserver` only fires on *changes* — a page sitting
still never re-fires whatever the code does. The check called "a post already
reported as seen is not reported again" was testing the browser's semantics, not
this app's. It has been replaced with the narrower claim the client actually
guarantees (one batch names each post once) with idempotence across renders left
where it belongs, on the server's MERGE, which has its own integration test.

That is the second time in two sessions a mutation run has found a green check
proving the wrong thing. The lesson is not about these two checks. It is that a
passing suite says nothing about which of its assertions would notice if the feature
were removed, and the only way to find out is to remove it.

## Part 17 — The reader curates the feed

A slider at the top of the feed, the same five notches as the one on each post. 0 is
chronological. Positive leans toward what you are predicted to resonate with;
negative leans the other way — which is not "show me things I hate" but "show me what
I might not like and feel compelled to witness anyway".

That second direction is the reason this is not a like-filter. The stated case for
it: *"sometimes a person wants to see new things that they might not like at all but
feel compelled to witness and understand, while other times they might be having a
rough day and need a pick me up."* Both are legitimate, they are opposite, and only
the reader knows which one today is.

### 17.1 Three promises, each enforced by a test

**Nothing is hidden, at any setting.** The lean reorders; it never filters. So there
is no value of the control that puts the reader in a state where something is being
kept from them. This is checked across all five settings in the browser, by asserting
the set of visible post ids is unchanged — and a mutation that drops one post per
page fails it.

**One move restores chronology, exactly.** `this.pulses` stays in the order the
server sent it and the lean is applied on the way to the screen, so returning to 0
gives the original order rather than an approximation, and no amount of leaning can
accumulate. A mutation that writes the reordered list back over `this.pulses` fails.

**Every post that moved says so.** A `↑4` marker whose tooltip reads "Moved up 4
places by your feed lean: this looks like something that resonates with you." The
setting is visible above; the effect is visible on each post. "Transparent algorithm"
is not a claim the code makes — it is a thing the reader can check.

An echo chamber is reachable from +2. That is deliberate: it is reachable by holding
the slider there on purpose, which is a choice the reader can see themselves making,
rather than one made for them.

### 17.2 The whole rule is one line

```
newPosition = chronologicalPosition - (lean / 2) * predicted * count
```

`lean / 2` is 0.5 at one notch and 1.0 at two, so two notches can move a
strongly-predicted post the length of the list and one notch moves it half — a nudge
that leaves chronology legible. The sign of `lean` flips the direction, which is what
makes −2 mean "surface the dissonant" rather than "surface less of everything".

**A post with no prediction does not move.** This is the case that dominates early
on, when almost nothing has a prediction. If unknown sank, every unrated post would
pile at the bottom and the feed would look broken rather than chronological.

The sort falls back to the original index, so posts that score identically keep
chronological order. A feed that reshuffles posts the model cannot tell apart reads
as randomness, and destroys the one ordering the reader can predict.

### 17.3 Client-side, deliberately

The lean arranges the posts the reader already has. It does not refetch and it does
not rank on the server.

Ranking server-side would mean the reader asks for a page and a model decides what is
in it, which is the thing this is meant to be an alternative to. Here the reader has
the posts, and chooses how to arrange what they have — so the lean cannot be the
mechanism by which something never reaches them. The description strings say
"the posts you have loaded" for exactly this reason: a wording that implied the whole
feed would be claiming more than the code does.

### 17.4 Six mutations, four of which found a weak test

The unit tests passed on the first run and **four of the six mutations survived
them**. Each survival was a different way for a test to look stronger than it was, and
they are worth recording because none of them is unusual:

| Mutation | Why it survived |
|---|---|
| Unknown predictions sink to the bottom | The test used a feed where *every* post was unknown. Sinking them all leaves the order identical. |
| Reversed the sort tiebreak | The "equal predictions keep order" fixture gave four posts the same prediction — but score is `index - move`, so equal predictions produce *different* scores and the tiebreak never ran. |
| Removed the clamp | The fixture had one predicted post, and with only one, any strong lean puts it first. Clamping was invisible. |
| `typeof === 'number'` → truthiness | The test asserted that `predicted: 0` differs from `predicted: null`. In this function they do not — both mean no movement. The test was asserting a distinction that does not exist here. |

The fixes were fixtures, not assertions: an unknown post pinned between
predicted-neutral neighbours; a fixture that produces a genuine score tie
(`0.5` at index 0 and `1.0` at index 1 both score −1); two mildly-predicted posts far
apart in time, where strength above 1 really does reorder; and an equivalence check
between a junk prediction and a missing one, since the guard's actual job is keeping
`NaN` out of the sort.

The fourth one is the most instructive: the test was not weak, it was **wrong**. It
described a behaviour the code does not have and never needed. Its replacement states
the equivalence explicitly, so nobody reads the absence as a gap:

> `predicted` 0 and `predicted` null move a post the same distance. They differ where
> the difference is visible to the reader — the gauge is drawn for one and not the
> other — not in the ordering.

All six mutations now fail, as do five mutations of the browser checks (filtering
instead of reordering, mutating the source list, dropping the markers, not persisting,
and never highlighting the state).

### 17.5 And one browser check that took the section down with it

The persistence check originally called `page.reload()`. That wiped the patched
`fetch` the whole feed section depends on, and every check after it failed — not
subtly, but with a 30-second timeout looking for an input that could no longer exist.

It now opens a **second page in the same context**, which shares `localStorage`
(the thing actually under test) while leaving the first page's fixture intact. It also
sets the lean to −2 first, because persisting the default proves nothing.

## Part 18 — "It skipped all the tests"

Reported after following the instructions exactly: the integration tests skipped
saying `NEO4J_URI is not set`, so the credentials were put in a `.env.local` copied
from `.env.example` — and nothing changed.

Nothing was wrong with what was done. There were **three stacked bugs**, each of
which alone was enough to produce that outcome, and behind them a fourth that was
worse.

### 18.1 Bug one: no env file was read by anything on that path

```python
pytestmark = pytest.mark.skipif(not os.getenv("NEO4J_URI"), ...)
```

The gate read `os.environ` directly. Nothing in the test path loaded a dotenv file,
so credentials in a file — any file, however named — could not be found. The only
route in was exporting shell variables.

`api/tests/conftest.py` now loads them before the test modules import, which is the
ordering that matters: a module-level `skipif` is evaluated at import, and pytest
imports conftest first.

### 18.2 Bug two: the file the instructions name is not the file the API read

`.env.example` said, in its first line, *"Copy to `.env.local`"* — correct, because it
began life as a frontend file and that is Vite's convention. `Settings` had
`env_file=".env"`.

So following the printed instruction produced a file the Python side never read, and
nothing reported it. `Settings` now reads `env_file=(".env", ".env.local")` with
`.env.local` winning, matching Vite's precedence so the two halves of the project
agree about which file is the more specific one.

### 18.3 Bug three: a copied example file has every setting commented out

Every server-side line in `.env.example` begins with `#`. Copying it wholesale gives
a file with all the right names and none of them in effect — which looks exactly like
a file being ignored.

The skip reason now names which of these is actually the case:

```
NEO4J_URI and NEO4J_PASSWORD not set — skipping Neo4j integration tests.
Found but COMMENTED OUT: .env.local:NEO4J_URI. Remove the leading '#'.
See api/README.md, or run: python scripts/check_neo4j.py
```

Four cases are distinguished: no file at all (naming the directory searched), a file
read with nothing relevant in it, values present but commented, and — for the Windows
trap where Notepad saving as `.env.local` without "All Files" produces
`.env.local.txt` while Explorer hides the extension — a file that *looks* right:

```
These look close but are not read: .env.local.txt. Rename to exactly
'.env.local' — an editor may have added an extension that Explorer hides.
```

`scripts/check_neo4j.py` had the same blindness, and it is the script the skip message
points at. It reads the files too now.

### 18.4 The one that mattered more: startup could hang forever

Making credentials findable exposed a real bug. Three unit-test files began hanging
with **no output at all** — not failing, hanging, during collection.

`TestClient(app)` used as a context manager runs the app's lifespan. That lifespan
already did the right thing in spirit:

```python
try:
    await db.init_driver(settings)
    await db.apply_schema(settings)
except Exception as exc:
    # Boot anyway so /health can report the failure; database routes 503.
```

But a `try/except` cannot catch a hang, only a raise. An unreachable host does not
raise — it blocks. DNS that never answers, or a paused Aura instance behind a TLS
handshake that never completes, held startup open indefinitely.

**On Render that is a deploy that never goes live and reports nothing.** The comment
said "boot anyway"; without a deadline that was aspirational. It now has one
(`startup_db_timeout_seconds`, default 20s — generous for a cold Aura instance waking
up, short enough that a deploy is not held open by a database that is never coming
back). Verified against a blackholed address: boots in 4s with the timeout set to 4,
and `/health` reports `database: unreachable`.

This bug predated the session's changes and was reachable in production the whole
time. It was only found because a test started hanging.

### 18.5 And the loader must not touch os.environ

The first version of the loader copied file values into `os.environ`. That was wrong
twice.

**It leaked between tests.** `monkeypatch.delenv(key, raising=False)` on a key that is
*absent* records nothing to undo, because there was nothing to delete. Code that then
*sets* that key leaves it set, with monkeypatch unaware it existed. `test_envfiles`
put `NEO4J_URI` into the session and `test_feed`'s "503 without a database" check
failed — only in a full-suite run, never when either file ran alone.

**It reconfigured the application under test.** `api.main` builds its `Settings` at
import from ambient config and the lifespan connects with them, so populating
`os.environ` made the *unit* tests open a connection to whatever database was in the
file.

The loader now keeps values in its own store and hands them out through `get()`, which
prefers the real environment. That precedence is a safety property, not a convention:
these tests write to whatever database they are given, so `NEO4J_URI=... pytest` has
to override a stale file rather than being quietly ignored by it. And conftest sets
`Settings.model_config["env_file"] = None` for the test run, so a developer's real
credentials cannot reconfigure the app under test.

### 18.6 A credentials file was committable

`.gitignore` listed `.env`, `.env.local`, `.env.*.local` by name. `.env.local.txt` —
the file a Windows editor actually produces, containing a real Neo4j password — matched
none of them and was perfectly committable. Now `.env*` with `!.env.example`.

### 18.7 Coverage

23 tests in `api/tests/test_envfiles.py`: precedence, parsing (quotes stripped, `=`
inside a password preserved, commented lines inert), each of the four skip-reason
cases, and that startup gives up on a database that never answers.

That last one is wrapped in a deadline of its own. A test for "this must not hang"
that hangs when it fails is nearly as useless as no test — it stops the suite dead
with no output instead of saying what broke. With the production timeout removed it
now fails in 5.8 seconds instead of hanging.

Six mutations of the loader are caught, including the safety-relevant one: a file
overriding the real environment.

## Part 19 — Convergent emergence

Concepts do not only branch. Some arise where several others flow together — the
Fractiverse's four axioms converging into Consciousness — and a tree cannot say that.
This part makes the model a DAG, and gives the cone a way to draw it.

### 19.1 Two relations, not one relation used twice

| | Question it answers | Cardinality |
|---|---|---|
| `parentId` | which cone am I inside, where do I live in the outline | exactly one |
| `emergesFrom` | what flowed together to make me | any number |

Consciousness is **inside** The Fractiverse and **emerges from** four axioms. Collapse
the two and you lose whichever half you collapsed: with only `parentId` you cannot say
what converged, and with only a parent list you cannot say where the node is filed.

Keeping `parentId` singular is what lets the Node Manager stay a file-system-like
outline. In Neo4j they are separate relationship types (`HAS_CHILD`, `EMERGES_FROM`) so
a traversal can ask for one without the other — which the tier computation needs.

### 19.2 The radial axis is Axiom IV

The design question was how to draw convergence in a cone. The answer follows from what
radius already means once you look at it:

- **Rim** — maximally differentiated. C₁ (Lattice, physical stability).
- **Axis** — maximally integrated. C₄ (Meta, unified realization).

Radius *is* the Crystallization Spectrum. So each extra parent pulls a node inward:

```js
pull = 1 / (1 + (degree - 1) * INWARD_PULL_PER_PARENT)
```

A reciprocal, not a subtraction, so it can never reach zero. A node with fifty parents
should *approach* the axis, never land on it and become indistinguishable from the apex
— and the apex is on the axis because it is total unity. Both ends of the axis mean the
same thing, which is what makes the diagram say something rather than merely arrange
things. A mutation to a linear falloff makes a 29-parent node land on the axis and fails.

The axis is drawn, dashed, apex to base. Without it an inward drift has nothing to be
inward of and reads as noise.

### 19.3 What a DAG breaks that a tree gave free

**Tiers can no longer be found by walking down from a root.**

```
tier(node) = 1 + max(tier(p) for p in [parentId, ...emergesFrom])
```

Taking the max over *both* relations is what makes the geometry mean anything: emergence
can never be drawn above something that feeds it. A node contained by a tier-1 parent but
fed by a tier-5 stream belongs at tier 6, not tier 2.

A breadth-first walk down `parentId` cannot express "wait until every contributor is
known" — it settles on whichever depth it reaches first. So this is Kahn's algorithm over
the union of both edge types. Nodes in a cycle are left at tier 0 and reported, because
the mutators refuse to build one but an imported file can contain one, and hanging is not
an acceptable response to bad data.

**Cycles can now close through an edge `childIds` knows nothing about.**

`getDescendantIds` follows containment only — correctly, since deleting a container must
not delete everything that ever emerged from it; a node drawing on Duality as one of four
streams is not inside Duality and must survive it. So reachability for cycle checks is a
separate walk across both relations.

The API's checker was a single chain walk up `parentId`. It is now a coloured depth-first
search, iterative so a deep chain cannot exhaust the stack. The colouring is what
distinguishes a **diamond** from a **loop** — and a diamond is the most likely shape in a
real map, so a checker that called it a cycle would be useless. Dropping the GREY marking
fails 12 tests, including "a convergent map is accepted".

**Deleting a node must strip references to it.** A dangling `emergesFrom` is worse than it
looks: the tier computation skips it, so the node keeps a tier it no longer earns, and the
API refuses to save the map at all.

### 19.4 A DAG in an outline

Three options exist and everyone who has tried this picked one: duplicate under every
parent, one home plus references, or abandon hierarchy. This is **one home plus
references**, and it is principled rather than a compromise because it is the same
distinction as the cone's: the containing parent is the scale, the others are streams.

A reference row is deliberately not a `.nodemgr-row` and carries no `nodeId` dataset — it
must not read as a second home, and the toolbar must not act on it as one. A check asserts
the outline's row count still equals the node count; rendering references as real rows
fails it with 37 rows for 36 nodes.

Seen from the other side, the selected node lists what flows into it, with the containing
parent shown apart (dashed, prefixed "inside") because it decides filing rather than being
one of the streams. Showing them identically would erase the distinction the model rests on.

The "Emerges from" picker offers a numbered list of what is **actually eligible** rather
than prompting for an id nobody knows, or matching a label two nodes might share. So an
illegal choice is never on screen to be made: not itself, not the container (which would
double-count the convergence degree, moving the node toward the axis for nothing), and
nothing below it.

### 19.5 SKOS was already more capable than the app

`skos:broader` is many-to-many by design — multi-parent was native to the chosen format all
along. But the importer stored `parentIri` as a single field that each `skos:broader`
overwrote, so **importing a legitimate vocabulary with several broader concepts silently
kept only the last.** Live data loss on any real-world ontology file, and invisible: the
import succeeded and the map was simply missing edges.

Every parent is now emitted as `skos:broader`, since in SKOS terms every one of them is a
broader concept, with `fract:containedIn` naming which is the container — the one thing
SKOS cannot express. A foreign file without it takes the first `skos:broader` in document
order: arbitrary, but deterministic and stated, which beats keeping whichever was parsed
last.

### 19.6 Recursive cones

Descending into a node makes it the apex of its own cone, showing it and everything it
contains. Axiom III is what makes this the right representation rather than a convenience:
if the structure is self-similar across scales, then finding the same structure one scale
down is what the model says should happen.

The load-bearing property is that **descending is a view, not an edit.** Real depths belong
to the whole map; the view computes a local depth (`node.depth - apex.depth`) and never
writes it back. A mutation that rewrites depths instead fails with "the view rewrote the
model", which is exactly what it would be.

Three things follow from that:

- **The apex sits at local tier 0, radius 0** — on the axis, because within its own cone
  it is the unity everything below it flows from.
- **Membership is recomputed every frame** rather than cached. The cone redraws from
  `getGraph()` each frame precisely so it can never show a stale graph, and caching
  membership would reintroduce that: a node added while the cone is open would not appear.
  It is a walk over one subtree, which costs far less than drawing it.
- **The tier clamp uses this cone's floor**, not the map's. Otherwise scrolling down goes
  past the bottom into empty space.

**The inflow collar** is what the original sketch called for, with one change. The proposal
put the containing cone above the new apex as a node; that conflates two different
questions — *which cone am I inside* versus *what did I emerge from* — and worse, it hides
the contributors, which are the most interesting fact about an emergent node. So the collar
above the apex holds **all** the contributors, drawn small with lines converging down into
it, and it is deliberately not a tier: those nodes are not contained by the apex, they fed
it, and giving them a tier would say the opposite. The containing cone is a breadcrumb,
because that is navigation rather than ontology.

Descending also **brings the selection with it.** Without that the readout kept naming
whatever was selected before — typically a node not in this cone at all — so the cone
described something it was not showing.

### 19.7 A check that measured the wrong quantity

The geometry check originally measured a node's distance from the axis as screen `x`. It
passed. Then aiming the cone at the node made it fail.

In a side elevation `x = radius × sin(angle)` — so **a node at the front or back of the
cone sits at the horizontal centre whatever its radius.** The check had been measuring
radius × sin(angle) and calling it radius, and it only ever passed because the angle
happened not to be zero. The projection now carries `radius` explicitly and the checks
measure that, which is the actual claim.

Two neighbouring checks were also asserting state a previous block had changed: the readout
was read while a different node was selected, and "remove the one contributor" ran after a
block that deliberately attaches every contributor it can find. Both now establish their
own preconditions.

A fourth instance turned up in the recursion checks, and this one is the sharpest. The
check "the readout must not name a node outside this cone" passed with the feature deleted
— because a previous block had left the focus on the apex itself, so there was no outsider
to misname. It now focuses a node outside the subtree on purpose and records its name, and
the mutation fails.

That is four shared-state assumptions and two checks measuring something adjacent to what
they claimed, in one project. Both patterns are worth naming because they produce the same
symptom — a green check — and neither is visible by reading the test. Only removing the
feature tells you.

## Part 20 — Two questions the ontology answered

A real ontology arrived as a `.ttl` file, and running it through the importer answered
two open design questions better than reasoning about them had.

### 20.1 Content needs no third file

Asked whether the markdown behind each node needs its own export. It does not, and this
was checkable rather than arguable:

| Format | Carries content | As |
|---|---|---|
| JSON | yes | `metadata.content` |
| Turtle | yes | `schema:text` |

One file either way. A `.ttl` holds the structure, the convergence, the metadata and
every node's page — which is what makes it the better archive format of the two, not
just the more interoperable one.

### 20.2 On-axis is declared, after trying to derive it

The question: should C4 / Consciousness sit exactly on the cone's axis? The intuition is
right — the axis runs from the Fractiverse at the apex to full realization at the base,
the two points that are not partial — but the asymptotic inward pull can never reach 0.

So: derive it. Every rule that suggests itself founders on the same thing. "A node is on
the axis when nothing above it dead-ends outside its ancestry" sounds right until you run
it: in the real ontology, **Quantum Field Theory** — a consequence hanging off the side,
not an input — blocks the reunification of something it has nothing to do with.

Whether a node is where everything comes back together is a **claim about the ontology,
not a fact about its edges.** So `metadata.onAxis` is declared by the author, rides
through both formats already (`fract:onAxis` as a real `xsd:boolean`, no format change
needed), and the derivable part — which branches never rejoin — is *reported* instead of
being silently encoded in geometry.

That distinction is worth keeping: **geometry from declaration, diagnosis from analysis.**

### 20.3 What the importer found in the file

Running it revealed things reading it would not have:

- **Every stated tier matched the computed one except `quantum-field-theory`**, given as 7
  while its only edge puts it at 6. Stating tiers in a file can only disagree with its own
  edges, so the corrected version omits them.
- **Two of eight axioms had nothing flowing out of them** — Axiom IV and Candidate Axiom 3.
  Six axioms pair neatly into C1, C2 and C3; the two left over are exactly the pair that
  belongs at C4. The axiom that *states* the C1→C4 spectrum was not attached to the
  spectrum.
- **`stillness` had no descendants** while `motion` had twenty, making the duality a label
  on a branch that never happened. Axiom II names the pair directly — ordering (Structure)
  and dissociation (Reset) — which puts Structure on the still side.
- **`duality` was missing entirely**, so Motion and Stillness hung off the Fractiverse as
  two arbitrary children rather than as a pair.

The corrected file is `docs/ontology/fractiverse-ontology-v3.ttl`. With the gaps closed,
the axis runs Fractiverse (tier 0, radius 0) → Consciousness (tier 8, degree 6, radius 0),
only two dead ends remain — the terminus and one deliberate consequence — and the tier
invariant holds.

### 20.4 A default map, stored on the person

Which map opens on sign-in is now a profile field rather than browser state, because it is
a fact about the user and not about the device they happen to be signed in from.

Validated on **read**, not on write. A map can be deleted, or nominated and then handed to
someone else, long after the choice was made; checking only at write time would leave a
profile pointing at something unopenable and produce a failure on every sign-in with no
way to see why. The pointer is returned only while it still resolves to a map the caller
owns, so a stale one reads as "no default" and boot falls back to the most recently edited
map.

`/me` also moved from the feed client to the base client while doing this. It was never a
feed concern — it carries the display name, the avatar and now a *map* preference — and
the Maps panel needed the last of those without having any reason to hold a feed client.

## Part 21 — A relation that is allowed to be circular

Correcting a misreading of the ontology surfaced something the model could not express.

### 21.1 The misreading

I moved `Structure` under `Stillness`, reading Axiom II's "field-induced **ordering**
(Structure)" as the still pole of the duality. That was wrong, and wrong in a way worth
recording: `Stillness` here means **terminal entropy** — heat death, the end state.
Ordering is the *opposite* of that; it is something motion does. Stillness has no children
because nothing emerges from heat death, and everything in the observable universe has
motion. The change made the ontology worse and is undone.

The lesson is narrow but real: a plausible reading of source material is not a substitute
for the author's meaning, and "this branch has no children" is not automatically a gap.

### 21.2 What it surfaced

The framework is explicitly cyclical. Axiom II: persistence comes from "a recurrent cycle
of field-induced ordering and ion-induced randomized dissociation", and "Death (Key 13) is
not an end, but the mandatory refresh rate of the information field."

So terminal entropy returns to a new beginning. That is a **loop** — and tiers are
`1 + max(parents)`, which requires an acyclic graph. A loop leaves every node in it
unplaceable. The model could describe one turn of the cycle and not the turning.

### 21.3 The resolution: an edge that bears no tier

`resetsTo` is a third relation, and the only one permitted to be circular:

| Relation | Circular? | Bears a tier? |
|---|---|---|
| `parentId` | no | yes |
| `emergesFrom` | no | yes |
| `resetsTo` | **yes** | **no** |

It is excluded from `getAllParentIds`, from the tier computation, from the cycle guard, and
from the tier-ordering rule. That exclusion is the whole design: the edge says "this returns
to that" without claiming either derives from the other, so a hierarchy can state a loop
without collapsing.

Everything else follows. It is its own Neo4j relationship type (`RESETS_TO`) so no traversal
that computes depth has to remember to skip it. In Turtle it is `fract:resetsTo` rather than
`skos:broader`, because stating it as "broader" would put the loop *in* the hierarchy and a
reader following broader would walk into it. In the cone it is a bowed arc outside the body
with an arrowhead — bowed because a straight line from base to apex would run along the
axis, which already means something, and would read as containment between the two most
important nodes.

### 21.4 Two mutations that only bit after the fixture was fixed

Five mutations were run. Three failed immediately; two survived, and both survivals were
the fixture's fault rather than the assertion's.

**"A recurrence edge bears no tier"** passed with recurrence counted as a parent. The
fixture pointed the reset from a deep node to a shallow one — the heat-death-to-singularity
direction — and treating *that* as a parent edge is a harmless shortcut, not a loop. Turning
it around, so the singularity arises from the previous cycle's end state, closes a real loop
and collapses every tier. The semantically interesting direction turned out to be the one
that catches the bug.

**The API's cycle and tier checks** could both be made to include `resetsTo` with nothing
failing, because no API test had a recurrence edge that formed a loop. Three now do, and
they assert the cycle is **accepted** — the opposite of what every other cycle test in that
file asserts, which is exactly why they were missing.

That makes six weak fixtures found by mutation in this project, against zero found by
reading. The pattern is consistent enough to state plainly: when a mutation survives,
suspect the fixture before the assertion.

## Part 22 — Declaring a node on the axis, and making it installable

Two requests: a button that puts a node on the cone's central axis, and the app installable
from the browser as **Fractality Platform**.

### 22.1 The axis is a declaration, not a derivation

Part 20 established why: radial distance means Axiom IV's crystallization spectrum, rim = C₁
Lattice, axis = C₄ Meta. `_inwardPull()` already moves a node inward by how many streams
converge on it, `1 / (1 + (degree − 1) × 0.6)` — a reciprocal, so it approaches the axis and
never arrives. That is correct behaviour for convergence and useless for saying "this one is
*on* it": with 29 parents C4 still sits at 6% of its radius, and no threshold on parent count
can be right, because sibling branches like Quantum Field Theory have the same shape and
belong at the rim.

So `metadata.onAxis` is a **declared** property, and `_inwardPull()` returns `0` for it. The
button is in the Node Manager toolbar (`⌖ On axis`), it is a toggle, and it reports state in
three places at once — `aria-pressed` and `.active` on the button, `T⟨n⟩⌖` on the outline
row, "on the axis" in the page pane.

Two details worth recording:

**Pressing it off deletes the key rather than storing `false`.** `metadata` is exported
verbatim, so a graph of 10,000 nodes would otherwise carry 10,000 `onAxis: false` entries
that mean exactly what their absence means. The read is `=== true`, so a stored `false` would
behave identically and only bloat every export — which is why the mutation storing `false`
had to be caught by a check on the *exported* metadata, not on the geometry.

**It does not call `onGraphChanged()`.** Nothing about the axis moves a tier or invalidates a
layout, and the cone redraws from the graph every frame, so a re-render of the panel is the
whole of the work. Firing the graph-changed path would recompute tiers on every press.

The user's framing is worth keeping verbatim, because it says what this is for: *"eventually
we may come up with an algorithmic way of asserting where along the axis-edge boundary range
a node should fit, but for now, that button should be a good start."* The property is the
place that algorithm will eventually write to.

### 22.2 Installable: what it took

Four files, none of them large: `public/manifest.webmanifest`, `public/sw.js`, `src/pwa.js`,
and four generated icons. The icons are drawn — the cone in outline, its axis, the apex and a
node converging on the axis — at 192 and 512 in both `any` and `maskable`, plus an
apple-touch-icon and a favicon. `maskable` is a separate file rather than a second `purpose`
on the same one because Android crops a maskable icon to whatever shape the launcher uses;
artwork that fills its canvas loses its corners, so the maskable pair is the same drawing
inside a safe circle.

The dock's Install entry is **never greyed out**. `beforeinstallprompt` fires only sometimes,
never on iOS, and cannot be re-created once it has been used, so an entry that depended on it
would be dead most of the time. With no prompt captured it explains how to install by hand,
which is real information — and the dock's standing rule is that nothing in it is a
placeholder.

### 22.3 The service worker: what it does not do

A service worker is the one file that can break a web app permanently. It sits in front of
every request, it survives reloads, and a bad one serves a stale build to a user with no
obvious way out from inside the app. So the interesting part of `public/sw.js` is the list of
things it refuses:

| Rule | Why |
|---|---|
| GET only | nothing else is cacheable |
| cross-origin untouched | the API is another origin; this alone keeps every authenticated response out |
| same-origin API paths excluded by name | in case the API is ever put behind this host |
| any request with `Authorization` untouched | credentialed is per-user by definition |
| cache-first for `/assets/` only | a content hash is the only guarantee a cached file is still correct |
| network-first for navigation | a deploy is picked up the moment the user is online |
| only `response.ok && response.type === 'basic'` | an opaque or partial response would be indistinguishable from a real one on the next read |
| `skipWaiting` only when the page asks | replacing the worker under a running page leaves it half on each build |

Those eight rules are read out of the served source rather than exercised. That is a
deliberate inversion of the usual preference for behavioural tests: the failure
mode is a cache that outlives a session and hands one user's data to the next, and a
behavioural test that happened to miss it would be worse than no test at all.

`/icons/` was briefly in the cache-first branch, next to `/assets/`, under a comment that
called both "the build's hashed assets". Only one of them is. Icon filenames are fixed, so a
cache-first entry pins the old artwork until `VERSION` changes — a longer pin than any HTTP
header can undo, and precisely the footgun 22.4 exists to avoid. Icons now fall through to
the network, the installed app takes its icon from the OS anyway, and the fifth rule above asserts
that the cache-first condition names `/assets/` and nothing else.

In development the worker is not registered at all, and any leftover registration is
*unregistered* — a cached shell during development is a debugging session spent chasing a
build that is no longer on disk.

### 22.4 Two deploy footguns

Neither shows up locally, and both fail silently in production.

**`sw.js` must not be cached.** The browser re-fetches the worker script to look for updates;
if that fetch is answered from a CDN cache, the update is never seen, and the user cannot fix
it from inside the app. Browsers cap worker-script caching at 24 hours regardless of headers,
so the worst case is bounded — but a day of shipping to nobody is not a bound worth relying
on. `Cache-Control: no-cache` on `/sw.js`.

**`.webmanifest` may not get a content type Render recognises.** Chrome ignores a manifest
whose type is not JSON-ish, and the symptom is not an error but the *absence* of an install
option, with nothing in the console to say why. `Content-Type: application/manifest+json`
stated explicitly rather than trusted to a MIME table.

`/icons/*` gets a day with `must-revalidate`, for the reason in 22.3: `immutable` on a
non-hashed filename would pin the artwork for a year.

One caveat that applies to this whole block: `render.yaml` is a Blueprint, and both live
services were created by hand in the dashboard, so **Render is not reading this file**. These
headers have to be entered in the dashboard to take effect. The file is accurate
documentation of what the dashboard should say.

### 22.5 Mutations

Both mutations of the axis toggle were caught, and both by checks written against the thing
the feature is *for* rather than against the code:

| Mutation | Caught by |
|---|---|
| store `onAxis: false` instead of deleting the key | the check on exported metadata after a second press |
| set the property but show nothing | the row-marker and page-pane assertions |

The icon-size check needed a fix of its own first. It paired each measured image back to its
manifest entry **by `src`**, which is unique — until the mutation under test made two entries
share one, at which point the check compared an icon against its own declaration and passed.
Pairing by index instead. That is the seventh weak fixture mutation has found here, against
none found by reading; the rule holds: **when a mutation survives, suspect the fixture before
the assertion.**

## Part 23 — Moving the app to a subdomain, and one test that only ran once

### 23.1 A signature mistake in a test that never runs

The first live run of the new integration tests failed on one of them:
`repo.delete_map(settings, SUBJECT, summary.id)` — three arguments to a function that
takes two. Ownership is enforced in the route (`_require_owner`), not in the repository,
so `delete_map(settings, map_id)` is correct and the test was wrong.

The interesting part is *why it took a live database to find a typo*. The module is
skipped unless `NEO4J_URI` is set, and a skipped test is never checked for anything —
not arity, not spelling, not whether the function exists. So the only feedback loop for
that entire file was a two-minute run against AuraDB on the user's laptop.

`api/tests/test_integration_call_signatures.py` closes that. It parses the integration
module, finds every `repo.<name>(...)` call, and binds the arguments to the real
signature with `inspect` — the check Python does at call time, done statically, with no
database. 198 call sites, and the message names the file, the line and the true
signature. Reintroducing the original bug fails it in 0.6 seconds.

It carries a guard on itself, too: if the module were renamed or the `repo` alias
changed, every check would pass by finding nothing, so one assertion fails when the
count of discovered call sites falls off a cliff. A check that silently checks nothing
is worse than no check.

### 23.2 The origin is a decision with a deadline

The app is moving to a subdomain — `fp.fractiverse.com` — so the root domain can be a
landing page for the several platforms under it.

**Nothing in the application code depends on the hostname.** `base` is `'./'`, there is
no path-based routing, share links are `/?map=...`, `VITE_API_BASE` is an environment
variable, and the manifest's `start_url` and `scope` are `/` on whatever origin serves
them. The move is configuration: a custom domain, a DNS record, an entry in
`CORS_ORIGIN`, and the subdomain registered with Clerk.

One thing in the repository *looks* like it should follow the app and must not.
`https://fractiverse.com/ns#` in `src/data/turtle.js` is an RDF namespace IRI — an
identifier that happens to be spelled like an address. Namespace IRIs are not required
to resolve, and renaming one renames every term in the vocabulary, so a `.ttl` exported
before the change and one exported after would describe two unrelated ontologies. The
root domain names the *project*, which is exactly the role it is being promoted into.
The line now says so, because it is precisely the kind of thing a later cleanup would
"fix".

### 23.3 Why the timing was close to ideal rather than late

A PWA's identity — the installed app, the service-worker registration, the caches — is
scoped to an **origin** and cannot be migrated. An app installed from the root domain
keeps pointing at the root domain forever; there is no redirect that reaches an
installed copy, and a stale worker at an origin persists until something replaces it.

So the cost of this decision is a step function, and the step is the first install.
Verified before saying so: `public/sw.js` is not on `origin/main`, so the deployed site
has never served a service worker and no browser anywhere holds a registration for
`fractiverse.com`. The move needs no self-unregistering worker and orphans nothing.

Asked a day earlier the answer would have been the same. Asked after launch it would
have involved every installed copy. The order of operations that follows from this is in
`render.yaml`: app subdomain first, landing page last, both origins in `CORS_ORIGIN`
during the overlap.

### 23.4 What the apex is for

The root domain stops hosting the app and takes on three jobs instead, and they reinforce
each other:

| Role | Why it belongs at the apex |
|---|---|
| RDF namespace (`https://fractiverse.com/ns#`) | names the vocabulary; must not move with the app (23.2) |
| Clerk primary domain | the session cookie is scoped to it, so every subdomain beneath inherits sign-in |
| Landing page | points at `fp.` (Fractality Platform), `tef.` (The Extended Fractiverse), and what follows |

The Clerk row is the one with a deadline. A production instance is configured for one
primary domain; subdomains of it share a session, siblings of it do not. Primary = the
apex gives `fp.` and `tef.` a shared sign-in for free. Primary = `fp.` makes `tef.` a
sibling needing satellite-domain configuration and a cross-origin handoff, and changing
a live instance's primary domain later means new DNS records and invalidated sessions.
So the apex is Clerk's root even while nothing is served there.

Naming: initials (`fp.`, `tef.`) rather than something self-describing like `app.`. With
one application `app.` would be clearer; with siblings it identifies nothing, and the
landing page is the right place to expand the abbreviations. This reverses a suggestion
made one exchange earlier — the multi-platform plan is what changes the answer.

## Appendix — Preventing recurrence

`npm run health` checks for the specific failure modes documented above:

| Check | Catches |
|---|---|
| ESM parse of every JS file | escaped template literals, stray braces, truncation |
| `py_compile` of every Python file | merged lines, bad identifiers, indentation |
| Relative import resolution | modules that were never created, moved files |
| HTML `src`/`href` resolution | broken stylesheet and script links |
| Bare imports vs `package.json` | undeclared dependencies |
| Named imports vs target's exports | `import { x }` where the module never exported `x` |
| `\`` detection | template literals pasted escaped |
| ~20,000-byte file size | chat-window truncation |
| `def init(self` in Python | dunders eaten by a Markdown renderer |
| Contested layout declarations | one selector positioned from two stylesheets |

It exits non-zero on any error, so it can gate CI. It reads files, though — for
anything about whether the app is *usable*, see `npm run browser-check` and
Part 6.7. Comments are blanked before
the import scan so example code inside `/* */` is not reported — the naive
version produced two false positives on this repo.

**One practical habit** avoids nearly everything in Part 1: when copying code
out of a chat, use the code block's copy button rather than selecting rendered
text, and check the byte count of anything that lands near 20 kB.
